# WhatsApp plugin engineering and delivery plan

This is the detailed engineering specification for the accepted [requirements](requirements.md) and [architecture](high-level-design.md). The owner [approved this architecture](supporting/high-level-design/architecture-approval.md) and explicitly included documentation. The one ordered delivery inventory is [slices.json](slices.json); the [overview](overview.md) renders it. Estimates and evidence limitations appear below and in [fresh engineering evidence](supporting/implementation-plan/evidence-notes.md).

The owner [accepted the detailed scope and slices](supporting/implementation-plan/approval-record.md). The [exact provider source version and tested-account eligibility](supporting/implementation-plan/provider-source-notes.md) are recorded from the retained manual and direct owner messages. Historical agent-authored live-result claims supply no approval. Formal design readiness requires current review closure. This plan does not authorize product implementation or deployment. Linux primitive probes passed; complete runtime, real-endpoint and platform acceptance belongs to implementation before rollout.

## Ownership and compatibility

Ship optional `arbiter-whatsapp` from `plugins/whatsapp`, entry point `whatsapp = arbiter_whatsapp:plugin`, following the existing `arbiter.services` contract, Python/server compatibility line and release tooling. Use the server's injected `plugin_storage`, `artifact_store` and resolved configuration. Do not derive a second state root from the process working directory. Runtime/CLI configuration resolution must produce the same absolute storage root.

Modules own one responsibility: `config.py` policy/config validation, `transport.py` fixed provider requests, `credentials.py` protected binding and operator actions, `state.py` SQLite/locks, `updates.py` envelope projection and polling, `messages.py` send admission/results, `statuses.py` read/typing, `media.py` artifact/provider transfer. `__init__.py` registers available descriptors and routes operations through these components. No separate secret service, inbox protocol, administration HTTP route or caller-grant framework is added.

The plugin depends on a server release that contains its actual optional administration dispatch, nested schema generator and bounded artifact reader; set that exact minimum at implementation, retaining the current compatibility upper bound. A package must not claim compatibility with older servers missing these interfaces. Existing plugins need no hook and retain scalar/list validation and activation behavior. Until integration acceptance, this optional package is under development; intermediate slices register only implemented operations and do not ship successful placeholder handlers.

The final slice includes package discovery, test/lint lists, explicit release-package/notes/install maps and the zero-code suite dependency. `meta:all` continues to select only that dependency bundle. A new plugin release does not implicitly publish server or suite packages. Affected published packages receive their own towncrier fragments; this design-only change itself is not a released runtime feature.

## Configuration and admission

Keep exactly the eight account policy effects and defaults in the HLD. Register one account schema containing `credential` and `policy`, and one policy schema with the eight named fields. Preserve raw field values through composition (`Any` at the configuration boundary if necessary), then require `type(value) is bool` before constructing the immutable typed runtime policy. This avoids treating strings or integers as authorization booleans through OmegaConf coercion. Reject unknown fields, missing policy references, duplicate credential references, unsafe references and invalid binding/state before operations become ready. Omitted known policy fields become `true`.

A credential reference is an opaque `whatsapp/<name>` string, bounded to 256 UTF-8 bytes; `<name>` contains ASCII letters, digits, `_` and `-`. Resolve it to a SHA-256-derived filename inside the plugin-private root. Neither references nor account names are host paths or caller authorization tiers. Every reachable caller shares configured account policies. Only the operator can change configuration or binding records.

Use one effect table for actual invocation and `check_operation`. Determine every effect from the validated operation and message type. Reject unknown operations before any provider, storage reservation or artifact-consumption effect. `check_operation` can inspect committed local readiness and policy, but performs no provider request, enrollment, reservation, cursor mutation or artifact access bookkeeping. Resolved configuration is immutable for the runtime; removal of a policy field takes effect through normal activation/restart.

## Exact internal interfaces

- `ProviderClient.request(method, path, credential, *, query, json_body, multipart, deadline, response_limit)` returns a bounded typed response or safe classified transport failure. It never accepts an arbitrary origin or follows a redirect. Request callbacks and raw response bodies are not logged.
- `BindingStore.snapshot(reference)` returns one immutable `{schema_version, store_uuid, provider_id, token}` snapshot after protected-file checks and database consistency checks. Token bytes remain internal. Callers cannot observe a mixed identity/token pair.
- `StateStore.commit_poll(provider_id, expected_offset, next_offset, observed_sources, replay)` performs one transaction and checks any existing normal cursor. It cannot publish a normal cursor without its complete observed-source set.
- `StateStore.reserve_reply(provider_id, source_id, participant, payload_sha256)` either inserts a pending reservation, replays a matching terminal result, or returns an explicit conflict. It runs only under the account send lock.
- New `PluginArtifactStore.read_once(artifact_id, url, *, max_bytes, allowed_content_types)` returns an immutable `ArtifactBytes(content: bytes, filename, content_type, size, sha256)`. The server store implements parsing, inspection, validation, read lifetime and consumption together. It never returns a filesystem path or performs a network fetch.
- Optional plugin method `administer_account(action, account, resolved_accounts, resolved_policies, runtime_context, secret_input, challenge_output)` is called only by explicit local CLI dispatch. `action` is `enroll` or `replace`. The caller supplies bounded in-process secret input and terminal output, not an operation argument or HTTP endpoint. Absence of the hook produces a local unsupported result without changing other plugins.

These are additions to implement, not existing public APIs. Keep the hook out of the required `ServicePlugin` protocol so old plugins remain valid. Reuse existing service-runtime construction and injected dependencies rather than creating a parallel configuration system.

## Operator commands and private publication

The HLD explicitly assigns exact CLI shape to detailed design. Use the existing server command tree:

```text
arbiter-server --config-dir CONFIG bootstrap --plugin whatsapp --account creator
arbiter-server --config-dir CONFIG config activate --plugin whatsapp --account creator --enroll --token-stdin
arbiter-server --config-dir CONFIG config activate --plugin whatsapp --account creator --replace-credential --token-stdin
arbiter-server --config-dir CONFIG config check --live
```

`--enroll` and `--replace-credential` are mutually exclusive and require one explicit plugin/account. Reject them on deactivate, summary-only and multi-account selections. Interactive terminal use may omit `--token-stdin` and obtain hidden input; redirected input requires the flag. Read at most 8 KiB of token text plus one trailing line ending. Reject empty input, NUL/CR/LF within the token and oversize input. Do not echo it or put it in environment variables, process arguments, config output or diagnostics. Results report only account readiness, action status and safe errors.

Account activation/bootstrap preserves saved operator edits. Ordinary activation, template preview and configuration checks never secretly enroll or replace. Explicit enrollment first completes the normal configuration edit, then performs the hook; provider failure leaves configuration intact and the account unbound. Reopening the same explicit command reuses the saved configuration. `config check --live` can perform bounded read-only readiness verification of an existing binding; it never starts a challenge, publishes a credential or changes normal polling.

Protected root layout: `bindings/<sha256(reference)>.json`, persistent `locks/root-binding`, `locks/<sha256(reference)>.poll` and `.send`, and `state.sqlite`. On POSIX, require operator-owned non-symlink private directories and regular single-link files, mode `0700`/`0600`, with protected parents. Open with no-follow where available and compare path/fd identities. Do not silently chmod or replace an unsafe existing object. Windows uses owner/SYSTEM/Administrators DACL protection and reparse/parent checks corresponding to the existing authority patterns. A path that cannot be proved safe is unavailable.

Publish one complete bounded binding record, maximum 16 KiB, with schema version 1, the database's random `store_uuid`, opaque provider identity and token. Create its temporary file exclusively beside the destination under the root binding lock, enforce protection, write/flush/fsync, validate the complete record, then replace on the same filesystem. POSIX uses `os.replace` and directory flush; Windows uses same-volume `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)` and validated private ACLs. Readers close their file immediately after a bounded snapshot read; the token is not held as a long-lived open file. If protection/publication/flush fails, report uncertainty rather than claim activation. Preserve evidence for inspection; do not overwrite a valid record during recovery.

Create/validate the SQLite store before the first binding. A missing store with no bindings permits initialization under the root lock. Existing bindings plus missing, unreadable, unsupported-version or mismatched store UUID fail closed. State is not reconstructed from empty defaults. A valid binding defines enrollment; orphan database rows do not activate an account. Root-wide publication rechecks all committed records and rejects duplicate provider identities or references. Configuration changes/removal do not erase bindings or source/reply history.

## Enrollment and replacement sequences

Acquire the selected reference's poll lock nonblocking; another attempt returns `conflict/enrollment_in_progress`. Inspect local state before provider I/O. An already valid binding reports complete for enrollment. Replacement requires that existing binding. Never acquire an account lock while holding the root binding lock; take account lock first, then root lock only for local inspection/publication. No root binding lock spans a provider request.

For new enrollment, scan updates from zero using `limit=100`, `timeout=0`, at most 300 request starts and 1,500 seconds. The provider permits 15 update requests per rolling 60 seconds. One administrative scanner owns all request starts, including connect retries, with at least 4.1 seconds between starts measured by a monotonic clock. Disable hidden transport retries for these requests. On 429, retain the exact requested offset and back off for 4.1, 8.2, 16.4, 32.8, then 60 seconds; the next start must satisfy both pacing and backoff deadlines. Reset backoff after a non-429 response. Every request, retry and wait counts within the original request/time budget. Recheck both budgets immediately before starting a request; do not start another request after exhaustion. An in-flight DNS call retains the transport's declared wall-time limitation. This pacing prevents this invocation from exceeding the quota; it is not a global limiter for unsupported concurrent external roots.

Validate each envelope/cursor and require progress on nonempty pages. Keep the scan cursor, candidate identity and pacing/backoff state in memory. The first empty response must fit the scan budget: at most 29,900 entries plus that response without retries, and fewer with retries. Larger backlogs or exhausted budgets return bounded unavailable, leaving enrollment unbound or replacement unchanged; reopening starts a new scan. Document this capacity and the possible 25-minute scan. When any identity is already locally bound, stop without further candidate polling. A candidate may initially displace an active provider poll before its identity is known; the active call reports 409 without changing its local continuation. Do not retry that displaced poll automatically in the same operation.

The first 204 retains its requested cursor, including zero. After that scan, generate 128 unpredictable bits and display `Arbiter enrollment <code>` only on the current operator terminal. Poll forward with `limit=100`, `timeout=15` for at most 180 seconds/180 request starts, including pacing, waits and retries. Continue the same pacing/backoff deadlines across the scan-to-challenge boundary; 429 retries retain the exact offset. Accept only a new exact text match from a `user:` creator participant with one consistent provider identity. Reject malformed pages, inconsistent identities and nonprogress; old challenges and unrelated text do not authorize this attempt. A scan/challenge timeout leaves no active binding. Never persist the temporary cursor, token, challenge or backoff state. A new attempt requires a fresh challenge after its scan. Provider-retained challenges later remain ordinary updates and cannot authorize another attempt.

On proof, acquire the root binding lock, revalidate configuration/reference/store/identity uniqueness, prepare durable store rows, and atomically publish the binding. The database row may precede publication; a crash there leaves only inactive orphan state. The binding's single publication activates identity and credential together. On uncertain publication, inspect a protected valid record/store: valid commit means complete; no commit permits a fresh challenge only after consistency checks; inconsistent state requires operator recovery. Do not persist the pending token/challenge or resume an old challenge.

Replacement holds the poll lock and verifies the candidate against the existing provider identity with the same bounded read-only scan; at least one validated identity-bearing response must match. An empty or inconclusive scan cannot prove identity. Do not change normal cursors or sources during verification. Failed proof leaves local committed bytes unchanged. After proof, take the root lock, recheck the old record/store and publish the candidate token with the unchanged identity/UUID. In-flight operations may finish on their earlier complete snapshot. Provider regeneration may already have invalidated the old token; preserving its local bytes does not promise provider validity.

## Durable cursor, source and reply state

Use Python's SQLite library, one database per private plugin root. Set schema version 1, `foreign_keys=ON`, rollback journal `DELETE`, `synchronous=FULL`, 5-second busy timeout and a 256 MiB database page ceiling. The rollback journal and bounded temporary publication need disk headroom; the ceiling is not a promise of total filesystem usage. No WAL checkpoint/lease/clock cleanup mechanism is added. Use `BEGIN IMMEDIATE` for state transitions and bound individual records/responses.

Tables and keys:

| Table | Key and fields |
| --- | --- |
| `store` | singleton key, random `store_uuid`, schema version |
| `agents` | `provider_id` primary key; nullable signed-64-bit `normal_offset` |
| `sources` | primary key `(provider_id, message_id)`; participant, provider timestamp, message type; foreign key to agent |
| `replies` | primary/foreign key `(provider_id, message_id)` to source; participant, canonical payload SHA256, state `pending/accepted/refused/unknown`, bounded result or safe error |

Store no message body/backlog, signed media URL, artifact capability or token in SQLite. Bound identity/message fields to 512 UTF-8 bytes, participant to 256, and stored result/error to 4 KiB. A duplicate source with inconsistent participant/type/timestamp is a protocol error and rolls back the whole page. Retain sources and reply rows indefinitely, across policy/config changes and restarts. Enforce 250,000 sources and 250,000 replies per root in addition to the page ceiling. New row admission stops at capacity; existing terminal replies remain readable. Never free a safety record merely because its timestamp is old. Operator recovery/migration preserves complete state; no unsafe reset/cleanup command is supplied.

A database/journal/lock file is protected as above. SQLite's transaction must not start on an unsafe/replaced path. Support only local filesystems with working SQLite and process-lock semantics; network/shared remote filesystems are outside the single-root ownership model. If a transaction or commit is uncertain, do not submit an effect that required it. If acceptance is known but result storage fails, retain pending protection and return partial failure with unsafe replay guidance. Disk exhaustion cannot erase previous rows or authorize another send.

Poll lock serializes runtime normal/replay polling, readiness checks that poll, enrollment and replacement for the same reference. A separate send lock serializes keyed sends/recovery for that account. Lock files persist and are never unlinked. POSIX uses nonblocking `flock`; Windows uses a persistent byte-range nonblocking lock. Contention returns a bounded conflict; process exit releases exclusion. SQLite transactions remain short and never span a provider request. Lock order is poll or send, then short root-binding inspection when needed, then SQLite; no reverse acquisition and no transaction while waiting for an account lock.

## Polling, projection and continuation

`receive_updates` uses the exact HLD signature. Require a nonnegative signed-64-bit offset when no normal cursor exists, and for every replay. A supplied normal offset must equal the committed normal cursor after initialization. Resolve this under the poll lock. Call `GET /agent/v1/updates` with fixed `limit=100`, `timeout=15` and the explicit resolved offset. A normal 204 commits/retains that request offset; replay 204 returns it without changing normal state. A 409, protocol failure or transaction failure does not change the cursor. Never compute the next cursor from a message count or timestamp.

Validate bounded JSON before starting the write transaction: object `whatsapp_agent_platform`; one `entry` with bound provider `id`; one `changes` element with field `messages`; value messaging_product `whatsapp`, contacts/messages/statuses arrays; exact integer `next_offset`. Nonempty responses must advance forward from the requested offset. Duplicate JSON keys, nonfinite numbers, mismatched identity, malformed known fields and unsupported envelope/type fail without cursor advancement. Unknown additive fields are discarded rather than returned as raw provider data.

Project contacts to `wa_id` and optional profile name. Project message `id`, `from`, timestamp, type and exactly its documented typed payload; supported inbound types are text, image, audio, video, document, static sticker and reaction. Project optional quoted context to its documented message/from fields. Reactions retain target ID/emoji but are never an outbound type. Receipt projection contains outbound ID, recipient, timestamp and documented `delivered/read` status. Status-only pages are valid. Do not create replyable sources from statuses. String/timestamp/digest fields are validated, not used as paths or authority.

For admitted messages, transactionally insert/check source identities with the exact provider cursor. For replay, insert/check sources but never change normal_offset. Return the known-field provider-shaped entry/change structure inside the HLD `updates` result; omit the top-level provider cursor from that inner object because `next_offset` is the operation result's continuation. Under ingress denial, replace every media payload with `{withheld: true}`, preserving envelope identity/type/timestamp and omitting ID, caption, filename, URL, MIME and digest. This projection cannot prevent the internal observation needed for deduplication, but returns no usable media handle.

Commit before returning. A response lost after commit can be recovered by explicit replay while provider retention permits. There is no local exactly-once inbox, automatic reply or hidden cursor reset.

## Typed messages and reply admission

Represent `Message` as a dataclass with required `type` string, optional `context: {message_id}`, and nullable fields `text`, `image`, `audio`, `video`, `document`, `sticker`. Each payload is a nested dataclass. Require exactly one payload, matching `type`; reject all unknown fields and unsupported combinations before a provider call. Text has nonempty `body` up to 4096 Unicode code points and optional boolean `preview_url=false`. Image/video/document have nonempty uploaded `id` and optional caption up to 1024 code points; document alone accepts filename up to 255 code points without path controls. Audio/sticker accept only uploaded `id`. Quoted provider context is separate from the local source key. Never infer the reply key from text or context.

The server schema addition recursively describes nested dataclasses with existing field metadata, requiredness and `additionalProperties=false`. Optional nested values describe null as well as their object shape. Reject recursive schemas and depth beyond 8 during descriptor generation. Existing scalar/list schemas and their public behavior remain unchanged. Validate type-specific cross-field rules in the plugin after the existing structured validator; invoke the same checks through catalog and HTTP entry points. Configuration booleans are validated before coercion as specified above.

Require `participant_id` in opaque `user:<nonempty>` form, at most 256 UTF-8 bytes, without controls. Preserve it exactly; never convert to a phone number. The provider enforces that it is the creator. A supplied source key must name an observed source for the bound identity and same participant. Canonicalize the complete outbound payload and participant after defaults/omissions are resolved, using sorted-key compact UTF-8 JSON and SHA256; include quoted context, captions, filenames and URL-preview choice. `reply_to_message_id` is the source identity, not a provider idempotency field.

After policy/argument/readiness checks, acquire the account send lock nonblocking. Failure returns `conflict/reply_in_progress` with safe same-key retry guidance. Under lock, compare or create the reservation in a committed transaction. Existing participant/payload mismatch returns `reply_payload_conflict`. Matching accepted/refused/unknown results are returned without transport. Pending found while this lock is now held has no live submitter in this root: change it durably to unknown before returning. Do not use PID liveness, elapsed leases or a wall-clock timeout to justify resending.

For a new reservation, commit pending before any request bytes can leave. Submit exactly once. A failure proved to occur before HTTP submission may remove that new pending row under the lock. A documented definitive refusal becomes `refused` with a bounded safe stored error. A valid success requires the documented product/contact echo and one nonempty provider message ID; store accepted before returning. Transport loss, ambiguous 5xx or malformed post-submission success becomes unknown; never automatically retry. A documented definitive not-accepted response can be refused, but a generic 5xx cannot establish that. If the terminal write fails, pending remains protective; report known acceptance as `partial_failure` with delivery information and `replay=unsafe`. A subsequent same-key call can conservatively return unknown after recovery.

Unkeyed proactive sends use the same validation, policy, private snapshot and transport, but no source reservation or durable exactly-once claim. An uncertain outcome returns unknown and unsafe retry guidance. Documentation requires automation to use the keyed path. A different endpoint or unkeyed call must not be advertised as recovery from an unknown keyed reply.

## Statuses, media and artifact lifetime

`mark_read` posts `{messaging_product: whatsapp, status: read, message_id}` to `/agent/v1/statuses` after read policy. `typing(active=true)` additionally sends `typing_indicator: {type: text}` and requires both permissions. False returns `upstream_rejected/typing_reset_unsupported`, transient no, replay safe, without I/O. Only HTTP 200 with boolean success true reports accepted. Do not retry ambiguous status writes automatically.

Upload uses multipart `messaging_product=whatsapp`, the validated MIME type and one binary file. Do not support host paths or arbitrary URL fetches. The artifact adapter parses only the exact current store base origin/path and one matching encoded artifact ID plus one nonce parameter; reject userinfo, fragments, extra/duplicate parameters, path traversal, mismatched ID and foreign origins before store access. Use existing artifact ID and nonce validation after decoding once.

Within the existing artifact root lock, perform purge/expiry, nonce/ID validation, stored size/content-type checks, bounded byte read, size/digest verification, then the existing exclusive consumed marker and access-record publication. Return bytes only after successful consumption bookkeeping. A failure before claim returns no bytes and consumes nothing; if access-record publication fails, use existing safe rollback behavior and return no bytes. Do not release the root lock between inspection/read/claim. Cleanup and HTTP reads use that same lock. No plugin transport holds the store lock. Match both declared MIME and actual stored content type against the provider-allowed set and size before consumption.

Use decimal byte ceilings from the manual: image 5,000,000; sticker 500,000; audio/video/document/generic binary 16,000,000, further limited by the server artifact cap. Images use JPEG/PNG; video MP4/3GPP; audio AAC, MP4, MPEG, AMR, Ogg/Opus; documents use the manual's PDF/text/Office MIME set; generic upload uses application/octet-stream. Return only the provider media ID after a validated response. A consumed input needs a fresh artifact after any later failure, including content validation or transport.

Use a maintained Pillow dependency in this optional plugin for bounded JPEG/PNG/WebP header/format/dimension validation after the read and before upload; no general transcoder or subprocess tool is added. Enforce image RGB/RGBA 8-bit and at most 25 megapixels, WebP at most 4096 by 4096, static/animated outbound support and no sticker captions. Do not decode unlimited pixels or disable decompression-bomb protection. MIME/size/container checks are local; provider acceptance remains authoritative for codec details not established locally. Incoming animated stickers remain unsupported per the retained manual. Pin and test the selected Pillow range with supported Python versions during packaging.

Metadata uses `GET /agent/v1/media/<encoded-id>` and verifies echoed ID, product, MIME, nonnegative size and a 64-hex SHA256. Incoming media digests use base64 of the same 32 bytes; never compare those two encodings as strings. `get_media` strips the signed URL. Download obtains fresh metadata for each operation and accepts only HTTPS `lookaside.fbsbx.com:443`, no userinfo/fragment, and exact `/agent/v1/media/<that-id>/content` path after safe single decoding. Preserve bounded signed query bytes for that request only. Reject all redirects before credentials can move. Download at most the smaller of declared/provider/server limits, require exact length and matching digest, then call the existing artifact create API. No provider URL or token is stored in the descriptor/source metadata. Capacity failure returns no descriptor.

Deletion posts no fabricated absence result: only the documented successful DELETE acknowledgement returns deleted. Unknown, expired, deleted and another-agent media may share `upstream_rejected/media_unavailable`; do not infer ownership. Delete does not retract a message previously delivered with that media. Sending uploaded media reuses the text slice's typed schemas, canonical payload/reservation and full send-plus-egress policy. Upload itself does not imply send permission.

## Transport, bounded errors and resource use

Use Python's `http.client.HTTPSConnection` with default certificate/hostname verification, fixed API host `api.whatsapp.com:443`, fixed `/agent/v1/` operation paths, no redirect handling, no environment proxy discovery and no HTTP debug logging. Never accept a caller-controlled host. Encode IDs only as one safe path segment; cap them at 256 ASCII letters/digits/underscore/hyphen (documented UUIDs fit). Attach bearer credentials only to the selected API/download host after validation. Close connections/responses in every outcome.

Use 5-second connect timeout, 20-second read timeout, and a checked monotonic 30-second per-request budget; poll request timeout is 15 seconds. Read JSON in chunks to at most 4 MiB, error bodies to 16 KiB and media to its admitted cap. Check remaining budget before connect, request submission and each read. OS DNS resolution may exceed the socket timeout; it occupies an existing bounded server worker and must not cause a new unbounded thread pool. After a DNS/budget overrun, do not start a provider write. Test this limit explicitly and document that the API does not promise a hard resolver deadline.

No automatic write retry, including upload/delete/status, occurs after possible submission. Read-only GETs may retry once for a connect failure before a response, within the original budget; never retry 409 inside a poll. The administrative scanner owns its explicit paced requests and bounded same-offset 429 recovery described above, with hidden transport retries disabled. Other operations return existing rate-limited guidance on provider 429; no new persistent local rate/burst limiter is invented. Root quota, response bounds and existing worker limits bound local aggregation.

Map argument/source/cursor conflicts to existing validation/conflict envelopes; policy denial to policy_denied; missing/unbound credentials to plugin_error/account_not_enrolled; token rejection to upstream_auth_failed; bounded read timeout to upstream_timeout; transient unavailable reads to upstream_unavailable; malformed JSON/schema to upstream_protocol_error; capacity to resource_exhausted; accepted-but-unrecorded sends to partial_failure. Store/return explicit transient and replay guidance. Any ambiguity after possible write submission is unsafe, regardless of a generic network error label. Keyed terminal replay always uses the same source key.

Use fixed public messages and allowlisted provider numeric error codes. Never serialize raw provider messages/bodies, exception text, auth headers, token values, provider identities, challenge text, artifact capabilities or signed URLs into diagnostics. Message/participant IDs can appear only in the authorized operation results where the HLD requires them. Log safe operation/domain/status/count fields and stack locations through existing redacted logging. Test stdout/stderr, native error serialization, configuration display, traces and dependency logging with synthetic canary secrets.

## Recovery, migration and acceptance

Support the existing server Python/OS matrix with local filesystems. Linux primitive feasibility is freshly exercised. macOS and Windows path protection, lock behavior, atomic replacement and SQLite crash recovery require platform tests in their owning slices. No silent downgrade to an unprotected file or unsupported replace API is permitted. Unsupported protection reports a bounded readiness failure before activating an account. A clean design review does not prove these implementation tests passed.

Migration is operator-offline: stop every old owner, validate a coherent snapshot, preserve protected binding files, store UUID, database and relevant lock/state layout together, copy to a supported protected destination, validate there before startup, then retire the old owner. Never run both roots, copy only tokens, reset cursors/replies while retaining credentials, or interpret missing state as a fresh account. A future schema migration must be explicit/versioned and preserve all safety rows; this first version needs no speculative migration framework.

Use deterministic HTTP-provider fixtures for all mandatory CI checks; fixtures contain synthetic identifiers/messages and exercise true request/response serialization. Separate tests kill subprocesses at the defined persistence/submission boundaries and race separate processes against the actual store and locks. Unit-only mocked calls cannot satisfy concurrency, catalog or platform acceptance. The final installed-package journey covers enrollment -> normal poll -> keyed reply -> replay -> media upload/send/download/delete -> replacement -> restart. Existing plugins and artifact HTTP reads receive regressions.

Live provider verification requires separate owner authorization, a dedicated eligible account and disposable-data scope. The retained source version and direct owner eligibility evidence are explicitly recorded; do not reuse discarded live-result prose as proof or generalize eligibility to other accounts. Implementation rollout additionally requires current sanitized fixtures for documented message/status/media behavior and independent integrated security acceptance. If provider evidence changes a public contract, return that choice to HLD review and human approval; do not patch it silently inside implementation.
