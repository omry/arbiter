# Authentication and mutual enrollment

Status: first-round product decisions approved by the owner on 2026-10-18;
technical design resumed with a corrected round-assessment workflow. Design
finalization requires DBB review, which has not started. The engineering protocol
and configuration profile remain incomplete. This document
describes design work, not implemented behavior, security validation or permission
to expose the current unauthenticated server remotely.

Review requirement: obtain the DBB assessment and disposition its findings before
finalizing this design. Interview approval does not waive this requirement or
approve an implementation. Record unresolved issues explicitly. The owner has
requested this review as a subsequent step; this note does not start an agent or
an automatic deep-design review loop.

## Goal and existing direction

Define an explicit flow in which a client establishes trust in the intended
Arbiter instance and Arbiter establishes trust in that client. Keep identity,
transport encryption and plugin policy distinct. Bidirectional information
exchange and challenges are possible tools; no protocol has been selected.

Approved transport direction (2026-10-19): native clients and Arbiter establish
an authenticated encrypted channel through any forwarding proxy. A separate
future browser administration interface continues to use ordinary browser HTTPS,
including Apache/Certbot deployments. Its login mechanism and delivery remain
separate work; the native channel must not require a browser extension or the
native client protocol for browser administration.

Setup priority (2026-10-19, owner clarification): the private Arbiter deployment
must be the easiest path to set up. Public DNS, Let's Encrypt/Certbot, exposing
the server to the Internet and manually provisioning a public certificate must
not become prerequisites for the baseline private installation or enrollment.
The existing self-signed transport plus approved operator-mediated pairing
remains the baseline candidate. Public certificates are an optional deployment
convenience. This priority does not approve accepting unauthenticated peers,
replace D77's long pairing secret with eight digits, or select the private
browser-admin trust/setup flow; that interface remains a design requirement.

The owner reaffirmed retaining the current pairing design after comparing
Codex-style device codes and certificate provisioning. Keep short-code/device-
flow improvements deferred; the discussion did not replace the approved long
pairing secret or mandate public certificates/TCP passthrough. Private browser
administration is explicitly on the remaining interview agenda. Its access UX
and initial browser trust must be resolved before the full design is finalized,
without turning browser UI implementation into part of this interview.

The owner wants to consider authentication before 1.0. The current scope is a
single owner who also operates Arbiter and supplies the upstream credentials.
Delivery slices remain to be decided. The first recovery implementation uses an
operator-held private backup key; passkey unlocking is future work.

Multi-owner hosting is deferred until there is a credible way to host other
people's secrets. In that future model, each owner has their own policies;
their agents see only that owner's listed accounts, subject to the agent's
account grants. This is a future isolation requirement, not a new policy layer
or a change to the current account-to-policy flow.

The first identity-provider implementation will deliver AMI only. External
identity-provider integrations are deferred. Preserve the general portability,
owner-authority, extensibility and transport-independent identity requirements.
Hermes and OpenClaw can use Arbiter tooling with AMI credentials; native reuse
of external identities is not in the first delivery. This scope decision does
not require a speculative provider framework.

AMI uses X.509 certificates as signed identity credentials binding durable
agent identity to its current public key. These credentials are independent of
HTTPS certificates and do not require TLS client authentication or a public CA.
The issuer and stable-identity profile, application proof protocol, validity,
revocation and recovery mechanics still require design.

## Current implementation

- Native HTTPS and self-signed or supplied certificate files exist in
  [server configuration](../server/src/arbiter_server/config.py).
- The [HTTP application](../server/src/arbiter_server/main.py) exposes discovery,
  operations and nonce-protected artifacts without a caller identity layer.
- The [native client](../client/go-cli/internal/arbiterhttp/client.go) supports
  certificate validation with a supplied CA. The
  [CLI](../client/go-cli/internal/cli/cli.go) skips certificate verification for
  loopback HTTPS when no CA file is configured.
- The [current security model](../website/docs/operate/security.md) restricts
  supported use to trusted local clients. The deployment operator controls
  service credentials, configuration and plugin policies. Caller identity and
  caller-specific account grants are absent; plugins already enforce their
  configured account policies.

These observations come from source inspection, not a new runtime or security
assessment. Existing HTTPS can be reused. Authentication will affect the server
request boundary, client credential/trust handling and installation flow.
The first authenticated release requires enrollment for every client invoking
service operations, including localhost clients. Existing callers must pair and
adopt the authenticated client contract. Migration instructions and exact
commands remain to be designed. General discovery requires authentication;
minimal health and pairing bootstrap are the public exceptions described below.

Approved account-information visibility: account discovery and direct lookup
require an authenticated client and expose only accounts granted to it. This
hides ungranted account names, descriptions, guidance and public settings,
including account information exposed through related discovery paths. This
policy applies consistently across those paths.

Approved anonymous API boundary: expose only a minimal health check and the
protocol/enrollment information and exchange needed to begin pairing. Require
authentication for the remaining discovery API, including plugin catalogs and
operation schemas. Preserve bounded operator-controlled enrollment windows;
public bootstrap does not open enrollment or grant service access. Exact
endpoints and public fields remain to be specified. Existing unauthenticated
discovery callers must enroll.

Approved revocation contract: revoke the client's authority, terminate its
active requests/downloads and reject subsequent requests. Target authenticated
client identity rather than IP address or assuming one TCP connection equals
one client; proxy/backend connections may be reused. This requires coordination
of active client access but does not require guaranteed cancellation of already
running upstream work. Such work may finish without returning its result to the
revoked client. Upstream changes already committed and data already delivered
cannot be recalled. Any continuing blocking work retains its admission capacity
until it actually finishes. Exact termination/check mechanisms and proxy
behavior remain to be designed and verified; no implementation is claimed.

Approved artifact policy: client-facing artifact metadata and downloads require
both the nonce and authentication as the client identity that produced the
artifact. A copied URL does not grant another client access. This restricts
URL sharing and requires authenticated downloads;
helpers using the same parent identity would remain compatible. Existing
artifacts lack client ownership records, so migration must not guess their
owner. Artifact expiry and one-time consumption remain separate controls.

Approved migration policy (Q25): invalidate existing pre-authentication artifact
links and delete their temporary server-side artifact payloads/metadata when
upgrading to the authenticated artifact contract. These entries have no client
owner and are stored in plaintext; do not guess ownership or preserve a
nonce-only access exception. Limit cleanup to legacy per-plugin `artifacts/`
entries. The artifact store shares the plugin data root, so cleanup must not
remove that root or unrelated plugin state. Upstream email and files already
saved on clients are outside this cleanup. Explain the link invalidation and
data loss in upgrade guidance. Arbiter has not been publicly released, so this
upgrade does not require a legacy artifact ownership/conversion flow. The
upgrade must not automatically replay operations to recreate artifacts.
This is an approved design policy; no files have been deleted.

### Agreed: encryption of stored and downloaded artifacts

Encrypt all artifacts by default, including retained server copies and files
downloaded and saved on the client. Ordinary operation responses have not been
brought into scope by this decision.

The approved direction is server-decryptable encryption for retained server
copies and recipient encryption for downloaded files. The client keeps saved
files encrypted by default and decrypts them when used. This assigns separate
server and client decryption authority; exact key management remains open.
An established file-encryption format must be evaluated; HPKE is
an available primitive, not a complete selected file format.
Server-authorized identity access plus nonce remains required under D48.

Future compatibility requirement: preserve Arbiter's ability to inspect upstream
plaintext for prompt-injection risks. This extends the existing
[data-filtering backlog direction](BACKLOG.md); it does not authorize building
a detector or claim that inspection can reliably eliminate prompt injection.
Inspection during initial processing can precede encryption, with any approved
transformation applied before encrypting the artifact that will be released.
Exact hooks, enforcement, resource limits and plaintext handling remain future
design work.

Preserving independent later inspection of retained server copies is approved.
This does not extend artifact retention or authorize inspection implementation.
Server storage encrypted exclusively to a client's key would prevent such
inspection. The earlier proposal to persist only client-decryptable ciphertext
on the server therefore does not satisfy the agreed compatibility requirement.
The revised split fits the trusted operator model: Arbiter can decrypt its
retained copy for future inspection; the client's saved copy requires the
client's private key. Concrete encryption and key-management mechanisms remain
unselected, including whether both copies share an encryption format.

This can protect copied artifact files and backups when the corresponding
private key is not also available. It does not protect against the trusted
Arbiter process/operator, which sees the upstream plaintext, or another local
actor that can read the client's private keys. Lightweight mode currently
accepts agent-readable keys; recipient encryption must not be presented as
same-host agent isolation. The future sandbox/broker boundary remains relevant.
Metadata and temporary plaintext copies require explicit handling as well.

Costs include authenticated binding of encryption keys to client identity,
encryption-aware save/view/stream commands and lifecycle handling. Do not assume
an authentication signing key is an encryption key. Rotation or owner-approved
identity recovery does not by itself recover files encrypted for a lost key;
retention of decryption keys or a recovery mechanism requires a separate policy.
Revocation cannot retract plaintext or decryptable ciphertext already obtained.
Encryption defaults and these decryption roles are approved design decisions.
The format and remaining key lifecycle remain open; no
encryption mechanism has been implemented.

### Agreed: explicit plaintext export

Name the plaintext export command `artifact save-decrypted` to make its effect
explicit. It replaces the current `artifact save` name in the proposed client
contract. This is for an explicit user request to retain a readable local file;
agents should prefer temporary-file or stdin processing for routine inspection.
Server storage and default recipient-encrypted delivery remain approved;
export decrypts at the client. No compatibility alias or transition behavior
has been selected, and the implemented CLI has not been renamed.

The earlier proposal for encrypted archives and owner recovery for `save`
does not follow from this plaintext-export use case and is not part of this
command's requirements. Key retention for remaining encrypted artifacts still
needs design.

### Agreed: explicit temporary decryption for tool processing

Allow a private, short-lived plaintext working file for tools that require a
path only when the caller supplies an explicit flag for passing that file to
the tool. The flag name remains unselected. Decrypted temporary-file creation
must not happen implicitly. This is a tool-processing exception, not general
persistent export; `save-decrypted` remains the deliberate export command.
Clean up the temporary file when processing finishes and prefer stdin when the
tool supports it.

Current `with-temp` already uses a private directory, mode-0600 file and deferred
cleanup, but does not have the new decryption flag. The approved exception
preserves path-based tool compatibility but cannot promise crash-proof deletion
or protection from other actors sharing the OS user. No encrypted filesystem
or memory-backed execution mechanism has been selected or implemented.

Research references: [HPKE](https://www.rfc-editor.org/rfc/rfc9180.html),
[age file format](https://age-encryption.org/v1), and
[X.509 key usages](https://www.rfc-editor.org/rfc/rfc9295.html).

## Technical proposal: artifact encryption lifecycle

This is partial technical synthesis, not a selected production dependency or
an approved client-file recovery policy. Authentication rekey and artifact
decryption are different lifecycles. Keep separate key material for these
purposes; do not delete a file-decryption key merely because the authentication
key reaches its 30-day rekey threshold. Any encryption-key replacement must
account for ciphertext still needed by the client.

Use independent server-storage and client-delivery encryption operations.
The server retains a copy it can decrypt for the approved future inspection
use case. On an authorized download it decrypts that copy and encrypts delivery
for the client's authenticated recipient key. A public recipient supplied in
an arbitrary download request is not enough: bind recipient registration and
replacement to the enrollment's authenticated key/owner-approved lifecycle.
This does not make an agent's authentication signing key an encryption key.

An age v1 X25519 profile is a candidate established file format. It provides
streaming authenticated encryption, with fresh per-file secrets and separate
recipient wrapping, so copying file bytes does not also copy decryption
authority. Its encryption alone does not establish who produced the file.
The design still needs authenticated origin/metadata binding, limits and
truncation handling before tool use. See the [age format](https://age-encryption.org/v1)
and [Go implementation](https://github.com/FiloSottile/age).
The Python [pyrage bindings](https://github.com/woodruffw/pyrage) are a candidate
for using the same format without requiring an additional operator application;
native builds, supported wheels, streaming behavior, dependency advisories and
cross-language interoperability require verification. No library is installed,
selected or security-validated by this research.

### Streaming feasibility assessment (2026-10-19)

The released [pyrage 1.4.0 source](https://github.com/woodruffw/pyrage/blob/v1.4.0/src/lib.rs)
exports `encrypt_io` and `decrypt_io` with buffered, file-like input/output.
The byte-array convenience APIs are therefore not a reason to buffer complete
artifacts. However, the wrappers show no explicit GIL release, and output uses
Rust buffering without an explicit outer flush/error check. These are concrete
integration checks, not proof of a failure or of event-loop responsiveness.
A thread-pool submission alone does not establish that Python can continue
serving health checks during the native call. Test slow I/O, final short writes,
flush failures, cancellation and contention before selecting these bindings.

[PyPI's 1.4.0 release files](https://pypi.org/project/pyrage/1.4.0/#files)
provide CPython 3.10+ ABI3 wheels for Windows x86-64, glibc Linux x86-64/ARM64
and universal macOS, but no Windows ARM64 or musl wheel. This matches the server's
Python minimum in metadata; it does not establish native runtime compatibility.
Windows ARM64 would need an independently verified Rust source-build/wheel path.
The earlier Noise/cryptography experiment does not verify pyrage packaging.

The [Go age API](https://pkg.go.dev/filippo.io/age@v1.3.2)
exposes streaming readers and writers; encryption must check `Close` to finish
the final chunk. Its [v1.3.2 module](https://github.com/FiloSottile/age/blob/v1.3.2/go.mod)
declares Go 1.24.0, matching the current CLI's language floor. No dependency graph,
advisory scan, cross-language artifact experiment or platform execution has run
for this candidate. No extra helper executable, maintained fork or compiler-floor
change is selected by this assessment.

The [age format](https://age-encryption.org/v1) authenticates chunks and requires
an error if EOF arrives without a valid final chunk. A successfully decrypted
prefix is not proof that the complete artifact arrived. The client chooses the
processing mode, preserving the existing `with-stdin` and `with-temp` paths
(D83). `with-stdin` decrypts and streams authenticated chunks as they arrive;
a later integrity or truncation error must fail the operation, but cannot undo
effects the receiving tool already performed. Do not force full-download
buffering or a second decryption pass on this path.

`with-temp` completes the download and verification before starting the tool.
Its private plaintext temporary file remains subject to the explicitly approved
plaintext-file flag and processing-lifetime cleanup. A verification failure
must prevent tool startup and trigger cleanup of the partial file. This does
not promise crash-proof deletion. Neither path may report a partial download
as complete.

Also support an optional complete encrypted download followed by plaintext
streaming to the tool (D84). Store ciphertext in a private, size-bounded temporary
file and verify the complete artifact before starting the tool. Then decrypt
that same ciphertext into its stdin. No plaintext staging file is created.
Full verification can run while receiving the ciphertext, discarding the
decrypted output; supplying stdin afterward needs a second decryption pass.
This waits for the download to finish and uses temporary encrypted storage.
On download or verification failure, do not start the tool and clean up the
temporary data. Retain the required decryption key through processing and clean
up ciphertext afterward, without promising crash-proof deletion or atomic tool
execution. Immediate streaming and explicit plaintext temporary files remain
available. This is a client choice, not a new default or a mandatory buffering
requirement. The option's CLI spelling is not selected, and the crypto
integration remains unimplemented.

### Proposed artifact identity and recipient binding

This specifies application obligations within the agreed encryption direction;
the format/library profile still needs interoperability and security review.

Register a distinct artifact-decryption public key through the authenticated
enrollment channel, with proof that the client holds the corresponding private
key. Bind the record to the server enrollment and a key version. Do not accept
a replacement recipient from a URL, proxy header or arbitrary download argument.
Changing this key requires an authenticated update authorized for that enrollment,
proof of the new key and a conditional durable update. It neither rotates the
authentication credential nor changes account grants. Hold the selected key
version through each admitted download/processing operation; a concurrent update
must not silently redirect that operation to another recipient.

The operation's authenticated caller context determines artifact ownership.
Keep the plugin-facing creation interface free of a caller-supplied owner
override. Bind the resulting artifact reference to the server identity, local
enrollment, artifact identifier and plugin/account source. Helpers sharing the
same enrolled identity remain the same caller; an independently enrolled client
cannot download another client's artifact merely by gaining access to the same
upstream account or learning its nonce.

Split storage into encrypted content metadata/payload and a minimal private
authorization/lifecycle index. The index needs opaque artifact and enrollment
references, nonce verification state, storage-key version, physical allocation,
creation/access deadlines and consumption state so admission and cleanup can
run without decoding upstream content. Keep filenames, media types, plaintext
hashes and upstream source details in encrypted metadata. This index still
exposes activity and allocation information to someone who reads server storage;
storage encryption is not protection from the trusted server/operator.

For the candidate age path, encrypt sensitive metadata together with its payload
under a bounded, versioned application framing profile. Do not place sensitive
fields in the public age header or add a custom encryption primitive. The exact
framing and parser bounds remain explicit profile work, not a claim that age
itself defines Arbiter metadata or authenticates a sender. The
[stable age specification](https://c2sp.org/age@v1.1.0) defines the file-encryption
layer; the enclosing authenticated Arbiter channel supplies live server origin.

Carry the expected artifact identity, plaintext length/hash and selected recipient
version in the authenticated descriptor/download context. Check decrypted metadata
against that context before releasing payload bytes. Compute the plaintext length
and digest while processing and require a valid final encrypted chunk plus matching
length/digest before reporting complete success. Immediate streaming retains its
accepted partial-input risk; verified-download and plaintext-temp modes withhold
tool startup until these completion checks pass. Do not infer server origin from
the ability to decrypt an arbitrary age file: anyone with a public recipient key
can encrypt a new file to it. The temporary ciphertext and its trusted context
belong to one live client operation; standalone offline import/authentication of
encrypted archives is not introduced here.

On the server, authorize ownership and current access before decrypting content
or reserving the one-time GET. HEAD remains non-consuming. Once GET consumption
commits, later crypto/network failure does not reopen its nonce. Reject revoked
access and stop delivery under the existing cancellation contract. Keep crypto,
storage locks and backpressure outside the event loop with bounded admission;
retain capacity until underlying work ends. No new replay guarantee or bypass
of storage limits follows from encryption. Key-update crash recovery, the
complete framing profile and native worker behavior remain engineering work.

Client guidance must explain the processing tradeoffs (D85):

- Immediate streaming starts processing sooner and needs no temporary artifact
  storage. The tool can receive authentic but incomplete data; a later download
  failure cannot undo its earlier effects. Use it when the consumer can safely
  handle partial input.
- Verified encrypted download needs temporary disk capacity for the ciphertext
  and waits for the full download and verification before starting the tool.
  It then streams plaintext without a plaintext staging file. This prevents
  incomplete downloads from reaching the tool, but does not make the tool's
  execution atomic or prevent later local failures.
- A plaintext temporary file supports tools that require a pathname. Explain
  the explicit plaintext-file flag and cleanup limits before choosing it.

Expose this choice in client documentation and operation help. Do not describe
the first two modes as having identical completeness or storage guarantees,
and do not infer a default from this guidance.

Admission must precede starting crypto work. Cancellation must retain its slot
until the underlying operation actually finishes, with bounded backpressure and
all files closed. Reuse the existing admission lifetime requirements; do not
assume an unbounded thread queue or a cancelled await stops a native call.
Storage/delivery metadata binding and the precise processing path remain open.
This is source-level feasibility evidence, not a completed T4 design or a
security/interoperability signoff.

Retain bounded streaming and the existing plaintext size/count/storage limits.
Account for ciphertext and metadata overhead in physical storage admission;
encryption must not turn the 50 MiB artifact limit into a limit on ciphertext
that unexpectedly rejects a previously valid plaintext size. Keep plaintext
out of persistent staging files except the explicitly approved export/tool
paths. Sensitive metadata also needs encryption or an explicitly justified
minimal plaintext representation; its exact envelope remains work.

The current server consumes the nonce on GET before streaming. It retains the
payload until normal cleanup but rejects another GET even while those bytes
exist. HEAD does not consume it. Defaults remain ten minutes idle and 24 hours
maximum retention, with cleanup activity-based. Thus client key recovery cannot
promise another download merely because the server once held that artifact.
This observation does not authorize changing one-time GET or retention.

No long-term encrypted client archive use case has been established. Normal
artifact use is processing through stdin or a temporary working file; the
explicit durable plaintext export is `save-decrypted`. The earlier question
about archive recovery after loss of a client decryption key inferred an
additional use case and is withdrawn. It does not require a new owner decision
or add client-key escrow/backup machinery to this design. Keep decryption
working through an active processing operation and routine authentication rekey.
This does not promise secure deletion or a fixed lifetime for files left after
a crash or deliberately retained outside the normal workflow. If durable
encrypted archives are introduced later, design their retention and recovery
then. The approved server recovery bundle remains separate.

## Decisions from this interview

- Confidential execution to protect users from the host operator is interesting
  longer-term research. The owner explicitly deferred implementation; it is
  not a near-term authentication deliverable. Retain the exploration in the
  [hosted secret-execution backlog item](BACKLOG.md). No platform or protocol
  has been selected.
- The near-term model has a single owner and trusted operator who supplies the upstream
  service passwords. Protecting those passwords from that operator is outside
  this design's near-term scope. Credentials remain separated from agents.
  Multiple clients can enroll under that owner. Multi-owner hosting is deferred;
  remote deployment support and an authentication protocol still need design.
- Each enrolled client has a separate identity and credential. Clients can
  share approved service accounts, while the operator can restrict or revoke
  one client's access independently. AMI's X.509 credential format and the
  owner-approved pairing flow are selected; their engineering profile is open.
- Identity and enrollment must be friendly to existing agent systems,
  specifically Hermes and OpenClaw. Evaluate candidate systems against their
  existing integration paths, setup effort and credential handling before
  selecting a mechanism. Reuse of native identities is a research objective,
  not a claim that either agent already supports the proposed authentication.
- Clients using an existing identity establish or select it before enrollment.
  In the approved lightweight flow, the trusted server represents the owner
  and provisions the client identity during enrollment with owner approval.
  This revises the earlier requirement that every client establish an identity
  before enrollment. AMI uses X.509; external provider integration is deferred.
  Creating an identity does not itself establish mutual
  trust or grant account access.
- Enrollment is a standalone flow for adding clients to an existing server.
  Server setup may use that same flow for the first client. Each client needs
  its own identity, explicit approval, server trust and account grants. One
  person may perform both operator and client-side steps; setup does not grant
  the first client a separate trust shortcut. Hosted-service authority and
  onboarding remain to be designed.
- The future server admin interface is the intended place to view pending
  enrollments and approve or reject them. Initially, local server-side operator
  commands, used directly or through SSH, open enrollment and review, approve
  or reject requests. Existing trusted host administration establishes initial
  operator authority. The future interface is not a prerequisite for enrollment;
  its authentication and delivery timing remain open.
- Client-initiated enrollment uses operator-controlled windows. New requests
  are closed by default; the operator temporarily opens enrollment. Pending
  requests, request rates and request lifetimes are bounded. Each request still
  needs explicit approval before service access. Exact limits, administration
  commands and the trust-verification protocol remain open. Invitation-URL
  support in the first version has not been selected.
- When enrollment is closed, the client must receive actionable guidance on
  asking the operator to open it through trusted administration, then retrying
  enrollment. This guidance does not authorize the client to open enrollment.
  Exact commands and any operator-contact mechanism remain unselected.
- Enrollment must account for which configured accounts an agent may access.
  Account grants remain changeable afterward: an enrolled agent can receive
  access to additional accounts without enrolling as a new identity. Its owner
  can approve the agent and grant specific configured accounts. In the current
  scope, the owner is also the operator; separate cross-owner grant authority
  is deferred with multi-owner hosting. Account access and identity verification
  are distinct concerns.
- Establish bidirectional trust first: the client verifies the intended Arbiter
  instance, and Arbiter verifies the intended client identity. Account grants
  are separate authorization state and may be assigned or changed afterward.
  This ordering does not select direct trust versus owner-signed identity or
  a proof protocol, and trust establishment alone does not grant account access.
- The server needs an owner-registration flow so it can recognize the owner
  behind an agent attestation. Registration must establish the association
  between the intended owner and their cryptographic identity. The registration
  bootstrap and proof mechanism remain undecided. Registering additional owners
  and defining their authority are deferred with multi-owner hosting.
  This requirement does not select Buzz or permit public self-registration.
- Provide a lightweight identity setup choice for users for whom adopting
  Buzz would be too much setup. Buzz remains interesting, but its full
  application/workspace must not be assumed to be the required user journey.
  AMI with X.509 is the first delivery; Buzz integration is deferred. Do not
  require a separate identity application for the selected lightweight path.
- Identity must be usable without a mandatory central external system. Do not
  require an external vendor account, public identity directory or third-party
  signing service for the baseline owner/agent identity journey. Assess how
  identity creation, verification and key lifecycle work with operator-controlled
  infrastructure. This does not establish an air-gapped or offline requirement.
- Keep the design open to other identity providers that meet the requirements.
  Do not make enrollment and account grants depend on one provider's identity
  format. Evaluate providers against the same continuity, owner-proof,
  credential-control and dependency requirements. The integration interface,
  cross-provider identity linking remain future work. Deliver AMI first.
- Lightweight setup is the requirement. Self-identification is one candidate
  approach to evaluate, not a required or selected mechanism. Compare possible
  approaches without assuming users already have an external identity. The
  credential profile and detailed setup commands remain engineering work.
- For the lightweight path, installing Arbiter must be sufficient. Its CLI
  handles identity setup; users must not need an additional identity application
  or separately operated background service. Embedded libraries are acceptable,
  and compatible existing identities may be an optional convenience. This does
  not require a separate identity application. AMI and X.509 are selected;
  storage and credential profiles remain engineering work.
- Every supported identity system must let a registered owner authorize a
  replacement for an agent's lost private key while preserving the agent's
  enduring identity. This is a general requirement, not a feature limited to
  the lightweight path or one provider. Recovery proof, old-credential
  invalidation and owner recovery remain to be specified. Once verified, key
  replacement preserves existing server enrollments and account grants without
  another operator approval. Existing suspensions and revocations remain in
  effect; identity recovery does not reinstate revoked access.
- Only the owner may authorize recovery of their owner identity through an
  owner-controlled recovery mechanism. Authority to administer an Arbiter server
  does not confer authority to recover another owner's identity. Server-local
  access administration remains separate. The recovery mechanism remains open.
- Agent identity and verifiable ownership must remain portable across
  independent Arbiter servers, including after owner-authorized agent key
  replacement. Each server must be able to verify continuity without depending
  on another Arbiter server. Enrollment, account grants, suspensions and
  revocations remain independently controlled by each server. The identity
  system and continuity-proof mechanism remain to be selected.
- Agents may not create durable identities; durable agent identities require
  owner authorization. Transient helper agents act under the parent agent's
  enduring identity and permissions, potentially with an indicator
  of the helper or execution. Such an indicator is not itself a new durable
  identity. Sharing an identity does not select shared private keys: credential
  custody and helper attribution remain to be designed. Narrower helper access
  and scoped temporary credentials are deferred until a concrete use case
  emerges. No implementation-cost estimate has been established for that work.
- Lightweight mode permits the agent to read its own client private key.
  This approval extends the earlier POC-only acceptance to lightweight mode.
  Put `NEVER SHARE THIS` at the top of the key file. The
  warning is guidance, not an enforced protection: agent-controlled code can
  still copy or disclose the key and enable impersonation. This does not
  authorize access to owner or recovery keys. Reploy isolation remains a
  deferred future direction.
- A doctor diagnostic should warn when lightweight mode is active, once a
  supported secure mode is available to recommend. Explain that the agent can
  read and copy its client key and give guidance for switching to the supported
  alternative. No secure mode is implemented;
  exact diagnostic syntax and secure-mode availability checks remain open.
- The intended hardened architecture combines an isolated agent with a trusted
  broker that holds its private client key and performs Arbiter requests.
  Arbiter enforces service access and operation policy; Reploy supplies network,
  filesystem and host isolation. Reploy controlled sessions are the likely
  integration mechanism. This is future architecture, not implemented
  protection or a prerequisite for lightweight mode.
- AMI enrollment uses one operator-mediated random pairing secret to establish
  bidirectional trust. The client generates and displays a one-time secret;
  the owner copies it into trusted server administration and approves enrollment.
  An established authenticated pairing protocol must bind the intended client
  and server, then exchange and retain their trust information automatically.
  This supersedes the separate manual fingerprint-comparison requirement for
  this flow. The secret is not a public request number and must not be sent in
  the initial unverified network request. Protocol/library selection, attempt
  resource admission, trust persistence and rotation remain open. Pairing secret,
  attempt and lifetime defaults are specified below. Normal HTTPS
  certificate validation remains available when a trusted-CA certificate is used.
- For every identity provider and authentication mode, durable Arbiter and
  client identities and their established trust must be independent of HTTPS
  certificates. Replacing or renewing the transport certificate, or placing
  the same Arbiter instance behind a TLS-terminating proxy, must not require
  reenrollment or a new identity-trust confirmation from existing clients.
  Clients must still authenticate the previously trusted Arbiter identity at
  the application layer. This is a general architectural requirement, not an
  AMI-specific property. An unexpected change to that durable identity remains
  a separate trust event. Transport validation and migration mechanics must
  satisfy this requirement; no blanket TLS-verification bypass is selected.

## Technical synthesis: pairing

This is a technical proposal within the approved flow, not an implemented or
independently reviewed protocol. The copied secret authenticates a temporary
channel; durable identities are exchanged and retained through that channel.
Do not transmit the secret as a login password on the unverified connection.

### Common exchange and activation sequence

1. The client generates a fresh private key locally for this server enrollment and a public pending-request
   identifier. Its provisional local state survives interruption. It displays
   one copyable pairing value containing the public selector and secret.
   Public request metadata is bounded and cannot activate an identity.
2. Through trusted local/SSH server administration, the owner supplies the
   pairing value and approves that pending request. Accept the secret through
   a protected prompt/input rather than requiring it in command-line arguments,
   shell history or logs. No separate identity app or public relay is required.
3. Run an established authenticated key exchange. Bind its confirmed channel to
   the protocol version, roles, request identifier, proposed client key and
   durable server identity. Prove possession of the client key as part of the
   enrollment payload. A request identifier alone never proves approval.
4. Deliver the server trust record through the confirmed channel. The client
   persists it provisionally before requesting final issuance. Credentials,
   trust information and completion travel directly between client and server;
   the owner does not copy a return bundle or compare another fingerprint.
5. Commit the approved identity, credential and initial grants consistently on
   the server, then return the completion receipt. The client activates its
   local credential/trust state atomically before acknowledging completion.
   Pending keys cannot invoke ordinary operations merely by existing.
6. A lost final response or acknowledgement does not undo committed enrollment.
   A bounded receipt-retrieval path proves possession of the approved client key
   and uses the provisionally retained server trust; it retrieves the committed
   result rather than issuing a duplicate identity or adding grants again.
   Uncommitted expiry/rejection cleans provisional resources. Exact message
   schemas, remaining admission parameters and crash-state validation remain work.

Server and client key confirmations must complete before the channel is treated
as trusted. Retrying the enrolling client's network exchange never resets its
request's expiry or attempt budget and never bypasses operator approval.
Approval initially uses the server CLI, locally or over SSH; neither a web
interface nor a continuously open administrator connection is required. Closing
or reopening that CLI does not reset the pending enrollment's limits.
The trusted administration interface is distinct from unauthenticated bootstrap;
the proposed local control transport is described with the state model below.

The pairing exchange is only a trust bootstrap. Its confirmed channel carries
the durable public keys, credentials and trust records; private keys remain
local. Keys may be generated locally before pairing, as in the sequence above;
their public credentials become trusted through pairing. An established
authenticated exchange, bounded attempts and a short validity window must
protect this initial step: strong later keys cannot repair pairing with the
wrong party.

### Approved: copy-paste pairing secret; short codes deferred

The owner selected a larger random secret for the initial delivery, deferring
short, typable pairing codes to a future improvement. This supersedes the
earlier eight-decimal-digit choice. The client generates 32 bytes (256 bits)
using the operating system's secure random generator. Encode those bytes as
43 unpadded URL-safe Base64 characters for copy-paste. This is the secret alone;
the single copyable value also carries a separate public request selector and
version framing. Its total length is approximately 70–90 characters; the exact
framing remains engineering work.

The owner copies that value into trusted local/SSH server administration and
approves the bound pending request. Never send the secret itself in the initial
network request or treat it as a public selector. Establish and confirm an
authenticated channel using an existing protocol for high-entropy pre-shared
secrets, then exchange durable credentials through it. A larger secret makes
offline brute-force search infeasible; it does not by itself prevent public-key
substitution or authenticate an arbitrary exchange.

Keep the existing ten-minute lifetime from request creation and at most five
admitted pairing attempts per pending request, including failed or abandoned
exchanges. Both endpoints retain those bounds across network retries. Expiry
or exhaustion requires a fresh secret and owner approval; it does not lock an
existing enrolled identity. The twenty-pending-request cap and separate work/
message admission controls remain. These bounds limit active attempts and
resource use; secret strength addresses offline guessing.

Noise supports 32-byte PSKs. An illustrative profile is
`Noise_NNpsk0_25519_ChaChaPoly_SHA256`; the unmodified unauthenticated NN pattern
does not provide equivalent authentication. Python `noiseprotocol` and Go
`flynn/noise` are candidates exposing PSK configuration. No exact profile,
dependency or native-build architecture is selected by the long-secret
decision. Require the early Python/Go compatibility POC and library assessment
before relying on the path. In particular, the Python project's security-review
and platform-coverage limitations remain to be assessed. The experiment below
provides local interoperability and limited packaging/build evidence, without
establishing implementation security or full platform compatibility.
See the [Noise specification](https://noiseprotocol.org/noise.html#pre-shared-symmetric-keys),
[Python candidate](https://github.com/plizonczyk/noiseprotocol) and
[Go candidate](https://github.com/flynn/noise).

A future short-code mode would require a suitable PAKE or another established
short-code authentication protocol with its own assessed implementation. It
must not reuse the high-entropy PSK protocol with an eight-digit secret. The
previous PAKE investigations remain evidence for that deferred work; they do
not commit initial delivery to custom cryptographic bindings.

- Use exactly `Noise_NNpsk0_25519_ChaChaPoly_SHA256` and a decoded 32-byte PSK.

### Technical proposal: CLI approval and pending-state ownership

The following state model specifies proposed behavior within the approved
flow. It is not implemented or independently reviewed.

The server process owns enrollment transitions. The initial administrator CLI
uses a local Unix-domain control socket in a private directory owned by the
server account. Restrict the directory to that account and the socket to its
owner; do not expose this interface through the public HTTP listener or Apache.
Run the CLI locally, over SSH, or inside the server's container/namespace when
necessary. Root and the server account remain trusted administrators. This
adds no remote administrator credential or mandatory background service beyond
the existing server. Other operating-system transports require an equivalent
local access boundary; a loopback TCP listener alone does not provide that
boundary. Windows local administration remains a portability gap in this
proposal, not a decision to remove an existing supported platform. Python
provides Unix-domain stream support in
its [asyncio API](https://docs.python.org/3/library/asyncio-stream.html#asyncio.start_unix_server).

The CLI sends one bounded approval command and receives a receipt. It supplies
the code through a protected prompt, not an argument, environment variable or
log entry. The server accepts ownership of that command before acknowledging
it. The CLI can then exit while the client completes the exchange. If the
receipt is lost, querying the request reports its existing state; repeating
approval does not reset time or attempts or replace the approved public key.
An operator can still explicitly reject a pending request before commitment.

Each request has an independent public selector and immutable client public-key
binding. The secret code is not used as a database lookup key, and the public
request must not contain the code, its hash or another offline guessing oracle.
Display the selector alongside the encoded 256-bit secret as one copyable
pairing value. The selector identifies which pending request the CLI approves;
it adds no authentication strength and does not replace secret entropy.
Unverified display names are labels, not proof of ownership. The exact selector
encoding and CLI spelling remain to be specified without adding another
operator return handoff.

Use a transactional local store for pending state, durable identities,
credentials, grants and completion receipts. SQLite is the proposed store;
its [atomic commit behavior](https://www.sqlite.org/atomiccommit.html) supplies
the all-or-nothing database transition, subject to its filesystem assumptions.
Keep the database and journals private to the server account. Run blocking
storage and pairing work behind bounded admission, outside the event loop;
transaction contention must not queue unbounded work or block health checks.
Only the server process mutates live authorization state through this interface.

The approved default is twenty uncommitted enrollment requests server-wide,
configurable by the operator. Count pending, approved, exchanging and confirmed
requests against the same allowance. Reject new requests immediately when full;
do not create a waiting queue. Commit or terminal cleanup releases the slot.
This limit does not cap enrolled clients or consume their operation-worker
allowance. It bounds retained requests, not fair admission: spam during an open
window can still prevent a legitimate new enrollment. Bound creation rate,
message size, cryptographic work and terminal-record retention separately.

| State | Meaning and permitted transitions |
| --- | --- |
| Pending | Holds a public selector, immutable key binding, creation/deadline, attempt count and version. No identity or account access exists yet. |
| Approved | Trusted administration has approved that exact request and chosen initial grants. The code is available only to the bounded live pairing context. |
| Exchanging | Reserve an attempt durably before emitting its exchange response. At most one exchange per request runs at a time. A failed or abandoned exchange consumes that attempt. |
| Confirmed | Both peers have confirmed the pairing key; the client has retained provisional server trust. Recheck deadline, approval/version and configured accounts before commitment. |
| Committed | One transaction records the enduring identity, issued credential, selected grants and recoverable completion result. Return credentials only after commit. |
| Expired, exhausted or rejected | Deny completion and release provisional resources. Never reactivate merely because the CLI or client reconnects. |

Retransmission of a previously accepted message in the same exchange returns its
cached result; it is not a new password guess. A fresh cryptographic exchange
reserves another attempt. Conflicting messages for an existing exchange do not
overwrite its state. Do not serialize and replay a key-exchange implementation's
single-use state to achieve HTTP retry handling. On server restart, invalidate
uncommitted pairing contexts whose ephemeral secrets were lost and require fresh
pairing/approval. Keep durable committed identities and receipts. A CLI restart
alone has no such effect. Keep the pairing secret out of the authorization
database, logs and recovery exports; it belongs only to the bounded live
pairing context, not the durable client credential.

Signing a credential and committing its authorization are distinct operations.
If signing occurs before the transaction, keep the result private and discard
it if the final conditional transaction fails. The transaction rechecks that
approval has not been rejected, replaced or expired and that its key binding
still matches. Concurrent completion must resolve to the same committed result,
not another identity or duplicate grants. A later revocation always takes
precedence over retrieval of an old completion result.

Before submitting its final confirmation, the client persists its private key
and provisional server trust in private local files. After server commit, lost
responses can be recovered by proving possession of that same client key to
the retained server identity. This retrieval returns the committed result; it
does not create a new credential or restore revoked access. Terminal pending
records, cached exchange messages and completion receipts need bounded storage
and cleanup. The corresponding caps and retention profile remain open; expiry
checks must run when admitting or completing work, not depend solely on cleanup.

This closes neither the complete wire profile nor T5: numeric resource caps,
receipt retention, local client state format, clock handling, recovery consistency
and crash/cancellation acceptance checks remain work. The state model requires
tests for duplicate approval, concurrent completion, lost final responses,
restart before/after commit and revocation racing with receipt retrieval.

## Technical synthesis: portable identity and recovery

This is a partial engineering proposal. The X.509 issuer/identifier/validity
profile and signed continuity format remain open; this section does not select
an invented identity system or claim that certificates alone solve continuity.

Keep these records distinct:

- **Owner authority:** the issuer material and explicit trust configuration
  that permit verification of an owner's authority over a client. AMI manages
  issuance for the current trusted operator; an ordinary agent credential
  cannot act as an issuer or authorize another durable identity.
- **Enduring client reference:** the verified owner/client identity that an
  independently enrolled server remembers across key replacement. It is not
  a display name, HTTPS hostname, certificate serial number or current public
  key fingerprint. Select the standard identifier/profile before implementation.
- **Current credential:** a signed binding between that reference and a key,
  with its purpose, issuer, validity and revocation/continuity state checked.
  A new certificate is not automatically proof that an older credential has
  been superseded. Certificate serial numbers do not provide a general recovery
  ordering mechanism.
- **Local enrollment:** the server's account grants, suspension/revocation
  state, activity history and accepted credential state for that reference.
  Importing owner trust or verifying a credential does not create grants.

An identity-provider verification boundary must produce the verified owner and
client references, key/purpose and continuity result from evidence checked
against previously established trust. The request cannot nominate an arbitrary
new issuer and thereby recover an existing identity. External providers remain
future work; the boundary is not permission to deliver another provider now.
Do not copy an owner's private issuer/recovery key to agents or to another
independently operated server merely to support portable verification.

Routine rotation proves the currently accepted client key and possession of the
new local key. Owner-approved recovery has separate authority: possession of a
stolen old client key must not produce an owner-authorized recovery event or
block a later valid owner-authorized replacement. Each server retains sufficient
authenticated continuity state to reject rollback to a superseded credential.
The exact signed evidence, ordering and issuer delegation profile need assessment;
ordinary chain validation is insufficient. For example, Go's
[`Certificate.Verify`](https://pkg.go.dev/crypto/x509#Certificate.Verify) does
not itself check revocation.

Applying an accepted owner-recovery update must be an atomic local transition:
verify the authority and new-key proof, check continuity against remembered
state, replace accepted keys, invalidate old-key sessions and persist the new
state without changing the enduring identity or account grants. Preserve local
suspension and revocation. The result distinguishes replacement of credentials
from reinstatement of service access; it must not clear a local access denial.
Concurrent old-key rotation cannot reverse an applied owner recovery.

### Technical proposal: portable ownership versus local access

Provisionally accepted direction (D103, resolving U51): the owner accepts the
separate portable identity-key role for lightweight AMI, explicitly relying on
DBB review before finalization. Continue designing against this direction;
do not treat it as security signoff, production adoption or review authorization.
Portable identity and per-server authentication prove different things. An
ordinary access key for A must not become a credential for access or replacement
at B. A public name or UUID alone also cannot prove that a requester is the
agent whose ownership another issuer certified.

Candidate structure using existing X.509 mechanisms:

| Role | Private-key holder and permitted use |
| --- | --- |
| Owner issuer | The trusted AMI owner environment. Certifies the enduring agent identity; agents do not receive issuer or owner-recovery keys. |
| Portable agent identity | The client holds an owner-certified, non-CA identity key. Proves possession of that enduring identity during another server's enrollment. It grants no service access or account permissions. |
| Server-enrollment access | The client holds a separate key for each server, as approved in D72. Ordinary operations and local routine rotation use that key and the server's accepted enrollment state. |

The [SPIFFE X509-SVID profile](https://spiffe.io/docs/latest/spiffe-specs/x509-svid/)
is an existing candidate for URI-based leaf identity and CA/leaf restrictions.
Its [identity standard](https://spiffe.io/docs/latest/spiffe-specs/spiffe-id/)
allows operator-controlled trust domains without public DNS registration.
Using the profile would not require deploying SPIRE. Its precise Arbiter URI,
issuer and interoperability profile is not selected here. A self-asserted owner
name or a new trust-domain spelling is not trusted ownership evidence.

For first AMI enrollment, generate provisional identity/access keys locally;
the owner still authorizes creation of the enduring identity. Issue its owner
certificate only after that approval. For another server, verify the existing
identity against previously registered owner trust and prove possession before
binding its independently generated access key to the local enrollment. Public
owner trust can be imported without disclosing its private issuer key. Do not
silently trust an owner root supplied by the requesting agent merely because
it displays a familiar name.

Use [PKCS#10](https://www.rfc-editor.org/rfc/rfc2986.html) for requested-key
proof rather than an invented CSR/signature format. Match the request keys and
CSR contents to the approved pairing record; do not honor arbitrary issuer,
CA or identity claims in a CSR. A reusable CSR is not fresh proof that its
presenter holds the key. The existing identity must also prove live possession,
for example through certificate authentication on the verified native TLS
enrollment-control connection. That control role must not gain ordinary access.
The complete handoff/binding profile still requires validation; neither the
pairing POC nor bare X.509 chain verification proves this integration.

The portable key cannot authorize local key replacement at an already enrolled
server. Existing-server recovery still needs its explicit trusted owner approval;
neither a stolen A access key nor a stolen portable identity key can use this
path to replace B's accepted key. First enrollment with a new server also needs
that server's owner approval and explicit grants. No automatic admission of
all agents signed by an owner is added.

Lightweight mode would store the additional private identity key alongside its
client-managed credentials. Theft could permit presenting that identity during
new enrollment requests, but would not by itself grant existing server access.
The owner provisionally accepted this additional key in D103; its complete
lifecycle/profile remains subject to the required DBB review. It is not the
owner's issuer key. Per-server access keys retain the approved automatic
rotation and inactivity rules; replacing a portable ownership credential must
be authorized by its owner issuer and cannot silently replace local access
keys or clear denials. Loss/expiry of this portable credential need not interrupt
an otherwise valid existing enrollment, but it prevents proving ownership for
another enrollment until owner-authorized replacement. No portable-key rotation
interval, additional operator ceremony or production dependency is selected.

### Approved: authentication keys belong to a server enrollment

Generate a distinct authentication key locally for each client/server
enrollment. Keep the enduring client identity portable, but bind the access
credential to the target server's durable identity, not its hostname or HTTPS
certificate. A server accepts a key only for its own explicitly approved
enrollment. Presenting the same client identity or another server's valid
credential must not enroll it, replace the local key or grant access.

If the authentication key for server A is stolen, revoke and replace that
enrollment's credential on A. The stolen key cannot authenticate to B and does
not authorize replacing B's credential. No server registry, automatic server
discovery or cross-server notification is required. The earlier proposal to
notify every server assumed shared keys and an enrollment inventory; it was
not approved and is superseded by this decision. Its history remains in the
interview record.

Apply the existing owner approval, account grants, rotation and inactivity
rules to each server enrollment. Recovery preserves that enrollment's identity
and grants without clearing its suspension or revocation. Migration or HTTPS
certificate renewal that preserves the server's durable identity does not
create a different enrollment merely because its address or certificate changes.

This contains theft of an individual authentication key. An attacker who reads
the complete client credential directory may steal multiple enrollment keys;
that remains an accepted lightweight-mode risk. Owner/issuer/recovery-key
compromise is a different incident. The decision does not select artifact
encryption-key scope or add a client policy layer. The exact X.509 profile,
portable ownership proof and server-binding format remain technical work.

### Technical implications of enrollment-scoped keys

Keep a local credential record keyed by the trusted server identity and the
enduring client reference. Before trust is established, keep the newly generated
key in private pending state associated with the request identifier. Do not
derive private keys from URLs, the pairing code or a portable public identifier.
Only promote that record after the pairing exchange verifies the server identity
and the server commits the credential. A supplied URL is a destination, not
evidence that a credential belongs there.

At the server, chain/ownership verification and local key acceptance are
separate checks. Ordinary access must match the enrollment's accepted public
key and credential purpose as well as its client identity and active status.
A certificate for the same identity issued elsewhere cannot replace that key.
Routine rekey proves the currently accepted local key and the new local key;
owner-approved replacement uses the existing recovery authority. Both bind the
target server and enrollment. Neither accepts proof from another server's
credential as authority to alter the local credential.

The request/response authentication profile must cover the target server's
durable identity, request contents and freshness, rather than sign only a
portable client name. HTTP Message Signatures provides a candidate mechanism
for authenticated message components; the complete profile and replay state
remain to be specified. See [RFC 9421](https://www.rfc-editor.org/rfc/rfc9421.html).
This binding must protect artifact HEAD/GET and download/tool paths as well
as operation JSON. The current native client has separate HTTP construction
paths for those downloads, so adding authentication only to the operation
client is insufficient. Authentication headers and signed requests must not
be forwarded automatically to a different destination through redirects;
migration to a new URL retains the remembered server identity and requires
verification before sending an authenticated operation.

Sharing an enduring identity is already approved for transient helpers. Do not
reopen that principle when specifying installation credentials. A helper can
operate through its parent's existing Arbiter client/enrollment without a new
durable identity or separate enrollment for each helper. Helpers using the same
credential cannot be revoked independently; revoking that credential affects
all callers using it. Attribution labels do not create a separate authentication
or revocation boundary.

### Deferred extension: independent installation credentials

The owner approved deferring management of separately enrolled installations
under one enduring agent identity. Initial delivery keeps the existing AMI
new-identity enrollment, shared parent client for helpers, and separate
authentication keys for different server enrollments. Owner-approved recovery
can replace a lost or compromised enrollment credential while preserving its
identity and grants; it does not add a parallel installation credential.
Bounded credential overlap during routine rotation is a transition, not this
deferred feature. Lightweight mode cannot enforce physical installation
uniqueness or distinguish copies of the same credential.

Keep identity, enrollment, credential and account-grant records logically
separate. Do not use the current public key as the enduring identity or make
account grants properties of a particular key. This permits a future extension
with multiple owner-approved, independently revocable installation credentials
under the same identity and grants. Do not implement the additional approval
flow, credential-management commands or per-helper credentials now.

The future flow could attach a new installation's pairing request/key to an
existing identity through explicit trusted owner approval. Naming the identity
or knowing a pairing code alone would not authorize the association. Its final
UX and credential lifecycle require design when the use case is taken up.

## Proposed options and deferred work

X.509 is selected for AMI identity credentials; the complete authentication and
pairing protocols remain unselected. Confidential-execution
implementation is explicitly deferred as longer-term research.
The earlier [transport and identity notes](future/transport-and-identity.md)
provide historical context; their transport proposals are superseded and their
identity candidates are not binding selections for this design.

### Enrollment nonce and completion

The earlier proposal required a server-generated client-specific nonce handed
back through the operator. For AMI, the approved flow replaces that manual
return handoff with direct client/server completion after owner approval. Any
protocol nonce remains bound to the intended request and client; it is not a
generic invitation. The proof and nonce mechanism remain to be selected.

Direct delivery alone does not establish initial server trust. For AMI, the
operator-mediated secret pairing exchange supplies that authentication and
binds the trust information received by the client. No extra manual fingerprint
comparison is required in this flow. Reuse an established pairing protocol;
none has been selected or implemented. PAKE-based tools such as
[Magic Wormhole](https://magic-wormhole.readthedocs.io/en/latest/welcome.html)
provide a precedent, not a selected dependency or external relay requirement.

### Approved: planned server identity-key replacement

Approved server-authority lifecycle (D104, U52): support operator-triggered
replacement of the long-lived server identity key. Clients verify and adopt a
legitimate planned transition automatically, without routine re-pairing. Keep
scheduled periodic replacement out of the initial scope; no interval is selected.
The durable server identity stays the same. This key is separate from public
HTTPS certificates and agent access keys; do not inherit the client's 30-day
rotation timer. Moving the same server identity to another host or renewing its
HTTPS certificate does not itself require replacing the identity key.

Planned replacement supports deliberate retirement or an algorithm change; it
is not recovery from theft. A stolen old key can also endorse an attacker's
replacement. Compromise recovery requires an independent trusted owner path,
not automatic acceptance based only on that old key. The exact transition,
offline-client, restore and recovery mechanisms remain technical design work
subject to DBB review. This approval does not claim a working implementation.

Existing PKI mechanisms support old-key-authenticated planned root updates; see
[RFC 9483 section 4.3.2](https://www.rfc-editor.org/rfc/rfc9483.html#section-4.3.2).
That is not evidence that a compromised old key can prove a replacement is
legitimate. Recovery from untrusted/lost identity authority needs independent
owner trust establishment; its precise implementation still needs DBB assessment.
No CMP implementation, new root key or rollout has been created here. HTTPS
renewal and proxy changes remain covered by the existing independence requirement.

#### Technical proposal: planned trust-key transition

This proposal implements D104's trust boundary on paper. It is not a deployed
rollover, selected certificate profile or evidence of interoperability. Keep
server trust replacement separate from client access-key rotation, owner
identity issuance and the backup-signing key. Replacing one role must not
silently replace the others or widen their authority.

**Records and authority.** The client remembers the durable server reference,
its accepted server trust anchor and a local trust-record revision. The URL is
a route, not that reference. The server persists a replacement transaction
containing its server reference, predecessor/new anchor fingerprints, public
transition certificates and phase. A transaction identifier is for concurrency
and idempotency; it is not independent evidence of authority or a globally
ordered counter that survives arbitrary restores.

Use X.509 CA-key transition certificates, rather than inventing a signature
scheme for a JSON key-update object. The replacement public anchor must match
the new key certified by the previously trusted authority. Validate the
certificate path, constraints, purpose and identity binding through the final
T2 profile. Supplying an old and new certificate in one response does not by
itself establish that relationship. The standard root-update mechanism is the
one referenced above; adopting that mechanism does not require exposing a CMP
service or importing an entire CMP implementation.

**Preparation and activation.** Only trusted operator administration starts
the change. Generate the replacement private key locally. Stage its public
anchor, transition evidence and server presentation chain durably before
publishing any update. Check that the staged private key matches the new public
key and that both the current and replacement presentation chains validate in
the intended roles. A preparation failure leaves the current presentation and
authority untouched. Concurrent preparation is serialized against the exact
current authority; a stale command cannot overwrite a later activation.

Publish the public transition material and switch the preferred presentation
as one recoverable server generation. The server must remain reachable by a
client that still trusts the predecessor: either the presented chain verifies
to that remembered anchor, or a bounded unauthenticated retrieval supplies
public transition certificates which the client can validate from that anchor.
Unverified retrieval may supply public data only. It must not receive agent
certificates, artifact nonces, ordinary operations or account information.
No outer HTTPS certificate or proxy assertion can authorize the trust change.

**Client adoption.** Build the candidate verification context separately from
the active trust record. Require a valid transition from the currently accepted
anchor and then a successful native TLS handshake that proves the candidate
server holds the corresponding server credential for the same durable server
reference. An unsigned update hint, name match or increasing revision alone is
insufficient. Validate with normal certificate time and purpose checks; do not
accept an expired path simply to avoid asking the owner for recovery.

Atomically install the verified new trust record using compare-and-swap against
the predecessor revision. Shared helpers must reload after another process
updates the record, rather than accepting whichever response arrived last.
Only after durable installation does the client acknowledge adoption over the
verified native channel. Failure to save is a local failure, not a successful
adoption; retain the complete previous record and retry only the idempotent
control transaction. Do not replay an operation or consuming download.

**Disconnected clients and retirement.** Preserve public transition evidence
needed by supported offline clients; a client's failure to acknowledge does
not authorize extending its access or inactivity deadline. Existing inactivity,
revocation, grants and rotation obligations still apply. Server-side adoption
tracking is diagnostic and a retirement precondition, not authority to rewrite
a client's trust record. Acknowledgement loss is safe: a later authenticated
connection can report the same adopted anchor without creating another change.

Retirement must not require retaining an old private signing key merely to
serve already-created public certificates. Do not silently delete transition
evidence or expand the verifier to accept every historical root indefinitely.
The chain/history byte limit, supported transition depth, validity overlap and
exact retirement preflight remain T2/T5 design gaps. In particular, retaining
only one transition without restricting or assessing repeated operator changes
would strand a client that missed two replacements. There is no approved
additional cutoff, automatic retirement timer or root-history fallback policy.

**Restore and compromise.** Recovery bundles preserve the active authority and
in-progress transition transaction coherently. Restoring an older snapshot can
bring back an authority that an up-to-date client has already replaced. Do not
silently trust it again or borrow the client access-key predecessor fallback
for server trust. Report the trust mismatch and use the existing independent
owner-approved repair path when valid forward transition evidence is unavailable.
This preserves the accepted possibility of client repair after a stale restore;
it does not promise root rollback will be unattended.

If the predecessor key may be stolen, do not use its transition signature as
sufficient recovery evidence. Trusted owner administration must establish the
replacement independently, through the pairing/recovery path. Do not force
clients to accept a peer merely because it claims the expected server name.
No automatic discovery or cross-server recovery registry is introduced.

Required, unrun scenarios: current clients adopt while offline clients remain
able to verify; missed consecutive replacements; malformed or unrelated CA
transitions; wrong server reference; expiry; client/server crash at every
publication or persistence boundary; acknowledgement loss; concurrent helpers;
rollback to a stale backup; and compromise requiring independent repair.
Check unchanged grants, access-key deadlines, URL trust rules and operation
replay behavior. Full certificate profiles and concrete storage/transport
limits are still needed before this mechanism is implementation-ready.

### Public HTTPS certificates

Administration may be served through an Apache reverse proxy with Certbot-managed
public certificates so browsers trust its HTTPS endpoint. This is an optional
browser-facing deployment arrangement, separate from AMI identities and native
client pairing. It does not replace administrator authentication or select an
identity provider. The native Arbiter service need not use that public
certificate merely because the administration front end does.

The CA-validated path can use certificates obtained and renewed by Certbot,
including Let's Encrypt certificates for the service hostname. Arbiter already
accepts a supplied certificate chain and private key through
`arbiter.server.tls.source=CERT_FILES`, `cert_file` and `key_file`. This is source
inspection evidence, not an executed Certbot integration test. Renewal must be
followed by a reload or restart of the TLS-serving process; certificate hot
reload has not been verified. Certbot can also manage HTTPS at a reverse proxy,
but proxy integration and any client-certificate forwarding are not selected.

Public HTTPS server certificates authenticate the service hostname. They are
separate from AMI's authority to issue client identities; a publicly issued
server certificate does not give Arbiter CA signing authority over agent keys.
Keep HTTPS renewal independent of durable client identity and enrollment.

This independence applies to all Arbiter identity providers, not just AMI.
Existing clients must continue to recognize the same Arbiter instance behind
a new transport certificate or proxy. The durable identity proof belongs at
the application layer; the HTTPS certificate identifies the transport endpoint.
Exact channel authentication, encryption, replay protection, streaming and proxy
rules remain to be specified using established mechanisms. The previous
signature-only candidate cannot satisfy the newly approved confidentiality
requirement: signatures authenticate contents without hiding them
([RFC 9421 section 8.2](https://www.rfc-editor.org/rfc/rfc9421.html#section-8.2)).

### Approved: encrypted native API and browser administration

On 2026-10-19, the owner accepted encryption directly between native clients
and Arbiter regardless of the forwarding proxy, and explicitly retained the
future browser admin interface. This supersedes Q21/D60's decision not to
require an inner encrypted native API channel. It does not change the current
single-owner trust model or claim protection from the Arbiter operator/server.

The native client authenticates the durable Arbiter identity established by
pairing, and Arbiter authenticates the enrolled client. Ordinary native API
requests/results travel only after that authenticated encrypted channel is
established. An outer HTTPS proxy forwards ciphertext; changing its certificate
must not replace the remembered Arbiter identity or require reenrollment.
Proxy certificates alone do not authorize access to the inner channel. Routing
and traffic metadata may remain visible; the proxy can interrupt or deny service.
No channel protocol, TLS-verification bypass or plaintext fallback is selected
by this direction alone. Bootstrap, redirects, channel establishment and failure
handling need explicit rules before implementation.

Arbiter decrypts the native messages itself and still sees upstream plaintext
while enforcing policies and preparing responses. The future prompt-injection
inspection direction remains viable. Proxy confidentiality is distinct from
server-side storage encryption and the separately approved recipient encryption
of downloaded artifacts; preserve their access, retention and export rules.

Browser administration is a separate authenticated surface using normal HTTPS
and browser certificate validation, including a publicly trusted certificate at
Apache where configured. It need not use the native channel or install native
agent credentials. Its future login/session/authorization design must protect
administrator operations; the encrypted native endpoint must not introduce an
unauthenticated browser-admin path or a plaintext fallback to ordinary native
service operations. The admin UI is not brought into the current delivery by
this reminder. Initial owner approval through local/SSH CLI remains available.

The additional implementation cost is an authenticated channel/transport
adapter, bounded session/handshake state, streaming and reconnect behavior, and
tests through a real forwarding proxy. Prefer an existing mature protocol over
designing encryption primitives or assuming the pairing PSK profile can be
reused for ordinary API sessions. The temporary pairing secret is not a durable
API credential. These are engineering requirements for T3, not implemented or
security-reviewed behavior.

References: [Certbot user guide](https://eff-certbot.readthedocs.io/en/stable/using.html),
[Let's Encrypt validation methods](https://letsencrypt.org/docs/challenge-types/).

The Q37 proposal to register/endorse each unrelated self-signed proxy authority
is not selected. The owner chose the encrypted native channel instead. The
earlier discussion remains in the interview ledger as history, not a pending
decision or an additional operator step in the selected native-client flow.

### Technical candidate: TLS inside a proxy-forwarded tunnel

A concrete candidate is standard TLS 1.3 between the native client and Arbiter,
carried as opaque bytes over a dedicated WebSocket path. The outer HTTPS
connection may terminate at Apache, while the inner TLS connection terminates
only at Arbiter. Pairing supplies the trusted identity material for the inner
connection; its certificates/keys are separate from the outer HTTPS certificate.
The existing X.509 identity direction fits this candidate, but exact certificate
profiles, ownership/continuity and revocation checks still belong to T2.
This is a proposed protocol/transport combination, not selected or tested.

Python's standard `ssl` library provides TLS 1.3 and MemoryBIO operation in the
supported Python range, and Go's `crypto/tls.Client` can wrap a `net.Conn`.
That provides an existing cryptographic implementation for the byte channel
without turning the initial pairing PSK into a permanent secret. Source/API
checks establish feasibility only; no Python/Go TLS-over-WebSocket exchange,
real Apache deployment or cross-platform test has run here. Sources:
[Python 3.10 SSL](https://docs.python.org/3.10/library/ssl.html#memory-bio-support),
[Go TLS](https://pkg.go.dev/crypto/tls#Client).

The server would expose separate outer routes for minimal bootstrap, the opaque
native tunnel and future browser administration. Both the native route and
browser UI could share one public HTTPS port. Browser administration keeps
normal certificate validation and its own future administrator authentication;
it does not pass through the native tunnel or become an alternate plaintext
operation API. Native operations must never fall back to an outer plaintext
route when the tunnel or inner identity check fails.

Keep the existing core operation/artifact application and global admission
state. The adapter must propagate a caller identity derived from the verified
inner channel into request authorization; proxy-supplied certificate headers
are not that evidence. ASGI defines a TLS extension for verified peer-chain
metadata, but inspecting the installed Uvicorn 0.48.0 HTTP protocol code did
not establish such integration. Identity propagation, application lifecycle,
streaming/backpressure and cancellation are real adapter work to prove before
adoption. Do not create independent unbounded queues, duplicate artifact stores
or a second authorization path to avoid that work. A valid handshake alone
does not bypass current enrollment, grants, revocation or inactivity checks.

The deployment consequence is that a reverse proxy must forward WebSocket
upgrades/binary traffic on the native path and support the required stream
duration. Apache documents this capability, including cohosting ordinary HTTP
routes; modern Apache can handle upgrades through `mod_proxy_http`.
See [Apache's tunnel documentation](https://httpd.apache.org/docs/2.4/mod/mod_proxy_wstunnel.html).
This is ordinary reverse-proxy configuration. Q38 was withdrawn after the
Apache clarification; it is not an additional operator policy approval, and
the clarification does not select a final transport implementation.
Do not silently add an ordinary-HTTP encrypted-envelope fallback as a second
protocol. Outer-certificate handling, redirects, session bounds, reconnects,
resumption and failure semantics remain design work after that disposition.

### Technical proposal: integrate the encrypted native channel

Retain the current JSON HTTP API inside the authenticated channel. This is not
an MCP migration. Use the existing HTTP request/response and artifact streaming
contracts rather than inventing another operation message format. The initial
candidate carries HTTP/1.1 over inner TLS 1.3 over the WebSocket byte stream.
WebSocket frame boundaries are transport boundaries, not HTTP message or TLS
record boundaries. Use existing implementations for all three protocols.

The client needs one authenticated transport used by operation/discovery calls,
artifact HEAD/GET, stdout processing, temporary tool files and `save-decrypted`.
Today those artifact paths construct requests separately in `cli.go`; changing
only `arbiterhttp.Client.RunOperation` would leave the contract incomplete.
Resolve relative artifact paths against the remembered enrollment. Do not send
client credentials or artifact nonces to a new authority through automatic
redirects. A new deployment address must prove the same durable Arbiter identity
before an authenticated operation or download is sent. A redirect is never
permission to invoke an operation again or to enroll another server.

The outer public listener exposes only bounded bootstrap, the native tunnel
entry point and the future separately authenticated browser-admin surface.
It must not also publish ordinary operation/discovery/artifact routes outside
the inner channel. A WebSocket upgrade grants no service authority. Do not use
proxy headers, source addresses, browser cookies or outer TLS certificates as
evidence of an enrolled native caller. Transport errors must not trigger a
plaintext fallback. Native authentication material travels only inside the
authenticated inner connection. Browser administration continues to use normal
HTTPS and does not inherit the native transport's certificate rules.

The inner TLS verifier must check the paired server identity and purpose, and
verify the enrolled client's certificate/key. Chain validation is necessary
but insufficient: the accepted key, credential generation, revocation,
inactivity and account grants also come from Arbiter's authoritative local
state. T2 must define the exact identity certificate and issuer profiles.
Disable TLS early data for this candidate: TLS 1.3 0-RTT does not give the
ordinary handshake's replay guarantees. Start without session resumption so
there is no ticket-based path around credential replacement or revocation;
any later optimization must preserve those checks. TLS record replay protection
does not make an application operation safe to retry after a lost response.
See [TLS 1.3 replay considerations](https://www.rfc-editor.org/rfc/rfc8446.html#section-8).

The verified channel supplies an immutable caller context to the existing ASGI
application. Maintain one shared application/admission/store lifecycle; do not
instantiate an independent worker pool for every connection. Register active
requests and streams against the enrollment and its authority generation.
Check current authority before dispatch and invalidate registered work when
revocation, suspension or grant removal takes effect. Synchronize registration
with invalidation so work cannot escape termination by racing a state change.
Subsequent requests on an established connection must not rely on the old
handshake alone. Closing the affected channel stops delivery; existing blocking
work keeps its capacity until it actually exits. Already committed upstream
actions cannot be undone. Restricted rotation completion after grace expiry
must not become ordinary access through a previously authenticated connection.

Carry cancellation and backpressure through every layer. A lost WebSocket or
failed TLS stream closes its underlying resources and signals HTTP disconnect;
it does not enqueue a replacement operation. Keep the current shared admission
before operation-body reading, the 1 MiB body ceiling, and streaming capacity
ownership through file closure. Bound transport frame buffers, incomplete
handshakes and active channels separately: the eight blocking workers do not
bound idle tunnels or TLS handshakes. Numeric transport limits and overload
handling remain T5 work, not newly approved defaults. WebSocket control traffic
must not count as artifact payload progress for the download idle timer.
Open capacity decision U53: propose a configurable server-wide ceiling of 64
open native encrypted connections, counting both authenticating and established
tunnels. This is a proposed default, not approved or implemented. Reserve before
accepting the WebSocket/starting inner authentication, reject excess without
an unbounded waiting queue, and hold the slot through actual cleanup. Existing
connections continue; ordinary health and trusted local control do not consume
this native allowance. A connection cap does not cap enrolled identities, bound
all OS/listener resources, or replace separate handshake CPU/time/byte limits.
Helpers sharing one identity still consume a slot for each open connection.

Connection setup includes the outer connection, upgrade and inner handshake
under the existing separate connect budget; do not reset that budget at each
layer or turn it into a total artifact-download limit.

This proposal specifies integration obligations, not a demonstrated adapter.
The native transport trust profile below derives the outer/inner separation
from the approved certificate-independence requirement. It does not approve
a generic HTTPS verification bypass. An isolated channel integration check still needs to prove
verified peer identity reaches ASGI, streaming remains bounded through Apache,
the browser route coexists, wrong inner identity fails closed, and disconnect,
revocation and interrupted rotation retain their existing semantics. The
pairing POC does not supply that evidence. No new interoperability check,
production implementation or independent review ran for this section.

### Technical proposal: native transport trust and browser boundary

The native connection authenticates the durable paired Arbiter identity at the
inner TLS layer. Its outer WebSocket carrier is not an authenticated Arbiter
endpoint merely because its HTTPS certificate validates. Conversely, requiring
the owner to approve each new self-signed outer authority would reintroduce the
certificate dependency rejected in D40/D78. In this candidate, outer certificate
chain/hostname validation is not the native identity acceptance gate. Inner
certificate, purpose, remembered identity and enrollment checks remain mandatory.
A changed inner identity fails closed even when the outer certificate is valid.
This is an engineering consequence of the agreed end-to-end trust boundary,
not a new product option allowing unauthenticated ordinary API requests.

Implement that rule only in a dedicated carrier that returns an authenticated
inner stream, never in a general-purpose HTTP client. Keep outer and inner TLS
configurations separate. Do not inherit the outer carrier's validation settings
into the inner verifier, reuse its HTTP transport for ordinary operations or
offer an automatic fallback after inner authentication failure. The proposed
outer carrier remains WSS; do not silently switch schemes or destinations after
a failure. Bound and validate the HTTP upgrade, WebSocket and TLS inputs even
when an attacker controls the outer endpoint. This isolates certificate trust;
it does not permit malformed or obsolete TLS or an unbounded bootstrap parser.

The outer request contains routing and upgrade information, not enrollment
credentials, owner/client certificates, account names, artifact nonces or
browser-admin cookies. No persistent cookie jar or automatic authorization
headers belong on that transport. Only minimal public bootstrap/pending data
may precede authenticated pairing. The one-time secret and private keys never
travel there. Pairing must complete its PSK-authenticated exchange and bind the
request, roles, proposed client key and server identity before persisting trust.
After enrollment, complete and verify inner TLS before sending service requests.
Refusing an unexpected inner identity never triggers silent trust replacement.

These are layered-protocol requirements to assess in the adapter POC and DBB
review. Go documents that bypassing its default certificate validation does
not authenticate a peer by itself, and provides custom verification callbacks;
our inner identity check must perform real validation rather than return success
unconditionally. See [Go TLS configuration](https://pkg.go.dev/crypto/tls#Config).
No source-level API inspection proves the composed transport secure or tested.

Browser administration has a different endpoint: if HTTPS terminates at Apache,
Apache can read the admin requests, responses and session credentials, and can
change the delivered page. The native client's inner encryption does not protect
browser administration. Encrypting Apache's backend connection to Arbiter does
not hide this plaintext from Apache itself. This follows from TLS protecting
traffic between its endpoints, combined with HTTP request forwarding:
[TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446.html#section-1),
[Apache reverse proxy guide](https://httpd.apache.org/docs/2.4/howto/reverse_proxy.html).

Browser-admin deployment guidance (corrected U39): any TLS terminator that
serves administration must be treated as trusted with its plaintext and session
authority. This is a security assumption and deployment recommendation, not an
Arbiter-enforced allow/forbid switch. In the ordinary browser design, Arbiter
cannot reliably determine whether an upstream proxy terminated the browser's
TLS connection and then established a separate TLS connection to the backend.
Requiring HTTPS at Arbiter alone does not prove end-to-end browser TLS.
Document that direct/TCP-passthrough HTTPS avoids exposing admin plaintext to

### Proposal: direct enrollment of a known client

### Approved direction: Arbiter-managed identity (AMI)

For lightweight mode, the trusted Arbiter server represents the owner and
provisions new client identities with the owner's approval. This combines
identity issuance and enrollment, avoiding a separate owner-side issuer and
manual CSR handoff. This direction is approved for lightweight mode, extending
the initial POC proposal. Do not apply it automatically to external identities
or hosted deployments with owners distinct from the operator.

The owner, acting as the client operator, initiates enrollment from the client
side. The client software performs the protocol on the owner's behalf; it does
not independently decide to enroll or create a durable identity. Server-side
approval remains a separate authority step, even when the same person performs
both roles.

The approved flow is for the client to generate a key pair locally, submit
its public key in a pending request and display a one-time secret pairing code.
Through trusted server administration, the owner supplies that code and approves
the intended pairing. The secret authenticates the pairing exchange rather than
merely selecting a public request record. The server then assigns the durable client
identity and issues the corresponding credential. The client waits for approval
and receives its credential and completion messages directly from the server;
the owner does not manually pass a completion bundle back to it. The server
issues an X.509 agent identity certificate. Exact approval
binding, credentials and account-grant steps remain to be designed; this is not
a finalized protocol. The agreed name is Arbiter-managed identity (AMI).

Incomplete enrollment must not accumulate abandoned state on either side:

- Bound pending requests and their lifetimes. Rejection, cancellation and
  expiry must reclaim request state and provisional resources.
- Keep new local keys and credentials in recoverable provisional state until
  enrollment completes. Clean abandoned temporary files without deleting an
  existing identity or unrelated enrollment.
- Make retries resume the same attempt rather than create duplicate identities,
  credentials or grants. Recovery must cover crashes, disconnects and a lost
  completion response, including interruption after owner approval or issuance.
- Track issued credentials and any identity/grant changes through completion or
  explicit reconciliation. Do not leave orphaned authority, and do not delete a
  completed enrollment merely because its final acknowledgement was lost.

These are cleanup and recovery requirements, not a selected transaction or
storage protocol. Expiry values, retry rules, activation timing, audit retention
and acceptance tests remain to be specified.

#### Technical proposal: previous-credential recovery state

The client record belongs to the remembered server identity and enrollment,
not a URL. Store the preferred credential, at most one completed predecessor,
and at most one pending rotation with its request/binding and phase. A pending
candidate is required by the already agreed interrupted-rotation flow; it is
not an additional historical credential archive. Retain the certificate and
private key together. Neither a certificate serial nor a locally increasing
counter alone identifies a rotation across a restored server snapshot.

Before ordinary requests, authenticate the server and establish the client's
accepted enrollment context. If the server unambiguously rejects the preferred
credential, permit one predecessor authentication attempt within the original
connection/recovery budget. A network timeout, an unverified outer proxy error,
an operation failure or an explicit enrollment access denial is not that signal.
The server rechecks its current key acceptance and access state; the client
cache grants no server-side overlap or exception to revocation or inactivity.

Success with the predecessor records which key authenticated this connection.
It does not erase the preferred credential or roll back the local record.
Reconcile any pending rotation through authenticated control exchanges first.
A candidate bound to a different expected key or transaction cannot be blindly
submitted to the restored state. Resume a matching transaction, or use the
ordinary eligible rotation path bound to the key the server actually accepts.
Preserve that server's recorded deadline. An ambiguous result remains pending;
it does not authorize deleting a possibly activated candidate or making another
rotation to guess which result committed.

On confirmed activation, atomically persist the new preferred credential and
its actual accepted predecessor. For example, if a rollback accepts A while
the client preferred B, activating C from A retains A as the predecessor;
unaccepted B is not a second history slot. Retain the old complete local record
until the replacement is durably committed. Coordinate updates by shared
helpers, recheck the local record version before committing, and reload after
another process changes it. Do not hold that coordination lock while a tool
process or upstream email operation runs. Exact portable client persistence
and locking adapters remain an implementation prerequisite; rename alone is
not evidence of power-loss durability. SQLite's
[atomic-commit explanation](https://www.sqlite.org/atomiccommit.html) illustrates
the need for ordered durable writes, not selection of SQLite for the Go client.

Fallback and rotation completion do not replay application requests. If an
operation or consuming artifact GET might already have run, report the uncertain
result separately. This follows the existing no-replay requirement and the
[HTTP retry constraints](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2);
it is not a promise that a one-time GET can be retried safely. Expired or missing
history still uses owner-approved recovery. Deleting superseded key files is
logical cleanup, not a promise of secure erasure from SSDs or backups.

Required implementation scenarios: current-key success without fallback;
single-generation rollback recovered by the predecessor; older rollback needing
re-pairing; expired predecessor; revocation racing fallback; pending activation
reply lost before undo; helper updating the shared record concurrently; local
commit failing after server activation; proxy timeout; and uncertain SMTP or
artifact GET results. Check unchanged grants, preserved deadlines, one fallback
attempt and bounded key slots. These scenarios have not run.

Decision after assessing the staging alternative (D91, 2026-10-19): keep undo
for the first version. Reploy staging can provide optional additional validation;
it does not replace undo. Isolated agent test profiles are not added to scope.

Background: the owner suggested testing
restoration in Reploy staging to avoid dedicated undo machinery and noted the
separate default staging port. The checked blueprint publishes staging on 18075
and deployed service on 8075, with deployment-provided endpoint overrides.
This addresses listener conflicts, not all restore/fallback requirements.

The owner identified a further requirement: realistic testing needs several
already-paired agents. Durable server identity is independent of the URL/port,
so those agents could in principle recognize the restored server at a staging

can fork enrollment/rotation state. If a client saves a new key after rotating
against staging, production may still accept only its old key. Merely changing
the endpoint is therefore not a safe testing workflow. Older snapshots can also
predate the keys currently held by the agents.

Separate copies of client credential state in isolated test profiles are a
possible technical approach, not an approved feature or a demonstrated Reploy
capability. Such testing must also address the existing single-active-authority
requirement and real upstream side effects. No staging cutover, switch-back or

### Deferred future work: clustered Arbiter servers

After approving the maintenance-window migration, the owner proposed that a
client support several Arbiter servers hosting the same identity, to improve
redundancy and migration availability. Interpret this exploration as several
endpoints for one logical server identity; separate independently enrolled
Arbiter identities remain a different case. The owner explicitly deferred this
design space (D95): configuration synchronization, shared artifact management,
cluster management, replica coordination and multi-endpoint redundancy are not
part of the current work. Keep the architecture open to later design without
building a cluster framework now. D94's maintenance-window migration, old-URL
handoff, single active authority and restore undo remain the current direction.

Distinguish the client trust/address model from server availability. A remembered
server identity can have multiple authenticated endpoint candidates; each endpoint
must prove that identity before ordinary access, and endpoint changes must not
silently create another enrollment. This can help the client discover a moved
server even if the old URL is unavailable, provided the alternatives were learned
through a trusted path first. Endpoints alone do not supply current state.

Redundant server instances need one coherent authority for credentials, rotation,
grants, revocation and inactivity, as well as coordinated artifact ownership,
storage and one-time consumption. Copying a backup and private identity key to
two hosts does not provide this coordination. Active/passive requires a safe
promotion/handoff mechanism that prevents both becoming independent authorities;
active/active additionally requires concurrency control across the shared state.
Do not treat a shared network-mounted SQLite file as a demonstrated solution;
[SQLite's network-use guidance](https://www.sqlite.org/useovernet.html) identifies
locking and durability risks and describes alternatives. No distributed storage
or replication technology is selected here.

Failover also cannot blindly repeat an operation whose outcome is unknown.
[HTTP retry semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)
require special care for non-idempotent requests; switching hosts does not make
an uncertain email send safe to replay. Preserve the existing error/replay
contract and avoid promising uninterrupted operations from endpoint retry alone.
Multi-endpoint client scope, replica topology, state synchronization, fencing
and availability guarantees belong to that future design. See the
[cluster design backlog](BACKLOG.md#post-v1). No further cluster question round
or implementation is part of this authentication interview.

### Technical proposal: export completion and offline restore

This is a proposed mechanism within the approved backup/recovery contract,
not implemented tooling or a completed bundle-format/security assessment.

**Export.** The local administrator command requests a snapshot from the running
server's private control interface. Run capture/encryption behind bounded
admission outside the event loop; reject unavailable capacity rather than queue
unlimited exports. Select the configured recovery recipient once for that export.
The external job cannot choose a different recipient or request plaintext.

Capture authorization state as a consistent database snapshot, not by copying
live SQLite/WAL files independently. The proposed SQLite store can use the
[online backup API](https://www.sqlite.org/backup.html), available through
[Python's `Connection.backup`](https://docs.python.org/3.10/library/sqlite3.html#sqlite3.Connection.backup).
Bound lock waits and the overall capture lifetime: concurrent writes can cause
backup restarts, so an export must fail rather than retry indefinitely. Capture
the configuration generation, referenced key versions and configured credential
values consistently with that snapshot. Retain those referenced versions while
exporting; if a coherent capture cannot be established, fail instead of mixing
unrelated revisions. SQLite alone does not make separate files consistent.

Include only the agreed recovery contents. Capture the configured account
credentials through trusted internal capture, never the entire process environment
or redacted display output. Normalize restored secret references to private files
within the recovery target. Do not execute arbitrary configuration resolvers or
import additional plugins merely to construct an export. Exclude active sessions,
uncommitted pairing secrets, artifact downloads and unrelated host files.
The encrypted manifest must identify bundle/schema versions, server identity,
snapshot time/revision and every included component's length/hash.

Encrypt before bytes leave the server-side export boundary. Diagnostics belong
on a separate channel and contain neither credentials nor private recovery keys.
A partial encrypted stream is not a successful bundle: report success only after
crypto finalization and a checked close. The requesting job writes a distinct
partial destination and promotes it only after command/stream success. Preserve
the last successful bundle on failure. Local same-filesystem replacement can
use [`os.replace`](https://docs.python.org/3.10/library/os.html#os.replace);
that alone does not prove durability or provide atomic publication in a remote
storage service. The external job owns that service's completion checks.

**Restore.** Use trusted offline operator tooling, locally or over SSH; restoration
must not depend on the failed server answering an API call. The external backup
job does not gain restore authority. Supply the encrypted bundle and private
recovery key to the recovery tool without putting the key in arguments, logs
or normal persistent server configuration. Restore does not need working upstream
accounts or live account tests before it can recover their saved configuration.

Decrypt and validate in a private staging area before replacing live state.
Require complete authenticated input, supported schema, component lengths/hashes,
valid internal references and the saved identity/key bindings. Reject path traversal,
links, unexpected components and executable restore hooks; do not apply archive
ownership blindly on the new host. Bundle-origin verification must use trusted
information independent of a self-asserted signer inside the bundle. The exact
origin-evidence/format profile remains unresolved; decryption alone is insufficient.

Keep the target server stopped during activation and replace the restored
configuration, secrets, identity and authorization state as one recoverable
generation. A durable activation marker selects either the old complete generation
or the new one after a crash, never a mixture. Validation failure leaves the old
generation untouched. Platform-specific activation and private-file/ACL handling
must be checked before adoption. Staging may contain plaintext secrets, remains
operator-only, and needs cleanup after failure/restart; no secure-deletion promise
follows. The recovery key is not part of the installed restored server state.

Show the snapshot-date warning already approved in Q24. Do not add a permission
review, paused-access mode or second activation approval. Do not reset recorded
rotation/inactivity timestamps to extend their deadlines. Start the restored
server under its retained identity only after activation succeeds. For planned
migration, stop the source before the final capture, then activate the destination;
the control operation for final offline capture must use the same consistency
rules. An external synchronized lease/fencing service is not introduced here.

### Technical proposal: recovery-bundle origin verification

The encryption recipient is public. Someone who learns it can encrypt different
contents to the same recipient; successful decryption therefore does not alone
establish that this server produced the bundle. The existing source is the
[age format](https://c2sp.org/age@v1.1.0), not a sender-signature protocol.
This matters especially on a replacement host with no surviving server trust
record. A verification key taken only from the incoming bundle is self-asserted.

Approved recovery record (D101, resolving U49): the same protected data kept as
the recovery key includes an additional field for trusted public server
verification information. Keep one file, not another secret or file for the
operator to manage. Preserve the whole record for authenticated fresh-host
recovery. This approves the recovery-material shape, not a cryptographic library
or exact field name/serialization.

Proposed provisioning for that record: include the private age decryption
identity, the durable server identity and trusted public backup-verification
key. The operator obtains the public server material
through the already trusted local/SSH administration path when configuring
recovery. The private decryption identity is generated and retained on the
trusted operator side, outside the server and agent environment. Only its
public recipient is installed on the server. The server separately holds its
private backup-signing key; that key is not the operator's decryption key or an
agent authentication key. Both key purposes remain distinct.

This retains the one-file keep-it-safe UX, but it requires preserving trusted
public metadata with the private key. A bare private age key could decrypt a
bundle; without independent trusted verification material it would not satisfy
this origin-checking profile. Do not silently treat bare-key restoration as an
equally authenticated alternative. D101 approves retaining that public metadata
alongside the private key; exact file naming/serialization remains provisional.

Candidate signed-manifest profile: use standard JWS Compact Serialization with
an ES256 signature over the snapshot manifest, then include it and the payload
components inside the age-encrypted bundle. The manifest binds its recovery
purpose/schema, server identity, snapshot identifier/date, component names,
lengths and SHA-256 digests. Signature verification uses the exact encoded JWS
payload; do not reserialize JSON to recreate signed bytes. The restore parser
rejects duplicate header/manifest keys and checks its supported schema/purpose.
Select the verifier from the trusted recovery file, not a key URL, certificate
or JWK embedded by the bundle. Fix the permitted algorithm to ES256 and reject
`none`, algorithm substitution and unsupported header extensions. See
[JWS](https://www.rfc-editor.org/rfc/rfc7515.html) and
[ES256](https://www.rfc-editor.org/rfc/rfc7518.html#section-3.4).

Restore verifies the signature and expected server binding, complete age
finalization, and every component's declared length/hash before activating
anything. Signing a manifest does not authorize archive paths, hooks or arbitrary
configuration execution. Existing private staging and strict component checks
remain required. A correctly signed older bundle is still an older snapshot:
neither the signature nor its date proves it is the latest backup. Keep the
approved stale-snapshot warning; no automatic rollback prohibition is introduced.

Preserve the backup-signing private key in the encrypted application recovery
state and verify it matches the trusted public key during restore. Migration
then preserves bundle provenance without tying it to URL or HTTPS certificates.
Deliberately replacing that signing authority requires updating independently
held verification information; do not silently trust a replacement advertised
only inside an incoming bundle. This is distinct from routine client rotation.
Compromise of the server signing authority can permit forged bundles; signatures
do not protect against the trusted operator or repair that compromise.

Implementation feasibility, not adoption: the server already depends on
`cryptography>=42,<49`. [PyJWT's documented ES256 support](https://pyjwt.readthedocs.io/en/stable/usage.html#encoding-decoding-tokens-with-es256-ecdsa)
and its [fixed-algorithm verification guidance](https://pyjwt.readthedocs.io/en/stable/api.html)
provide a library path for this small signed manifest. Backup export/restore is
server-side Python work; it does not require adding JWT to the Go client.
PyJWT has not been installed, selected for production or assessed across the
repository's release matrix. Container framing, parser/capture limits and the
remaining private-file/activation adapters still need design and validation.

Required cases include a valid migration, a decryptable bundle signed by an
attacker, substituted verifier/key URL, wrong server identity, altered component,
duplicate JSON fields, truncated final ciphertext, a valid stale snapshot,
missing recovery metadata and mismatched restored signing key. These checks
have not run; the proposal is not a security-reviewed implementation.

This leaves explicit engineering work: cross-file capture/version ownership,
bundle framing/origin verification, numeric export bounds, snapshot staging,
portable activation and crash/cancellation tests. None has been executed or
security-validated by this design synthesis.

### Agreed: automatic client key rotation

Routine automatic rotation replaces a client's key pair and signed credential
without changing its durable identity. It limits how long the same key remains
in normal use and avoids recurring manual owner approval. This does not by
itself invalidate a stolen key or establish that a client is uncompromised.

The client generates a fresh key locally and requests a
replacement X.509 credential, authenticated with the current valid credential
and proof of the new key. Keep the same durable identity, enrollment and grants.
This routine rotation does not require fresh owner approval. Certificate
renewal using the same key is distinct from generating a new key pair.

Check whether rotation is due when the client establishes an authenticated
connection. Rotate when due; a new connection does not always require a new
key. The lightweight path does not require a separately operated background
service to maintain credentials. The default rotation threshold is a key age
of 30 days, checked on connection. It is not
a 30-day certificate lifetime or a requirement to rotate while idle.

The server starts the rotation-completion grace period when it durably prepares
a replacement during a client connection, not when the current key reaches
30 days of age. Preparation does not activate the replacement. The client first
verifies and durably saves it, then confirms possession of the new key. Only
that confirmation activates the replacement.

While confirmation is pending, the current credential remains usable for
ordinary operations until the fixed grace deadline. Missing confirmation alone
does not justify an earlier cutoff. Retries, reconnects, continued use of the
current key and replacement attempts cannot restart or extend that deadline.
If the deadline passes without completion, deny ordinary operations with the
old credential; retain only a restricted completion path for the pending
rotation. Revocation, suspension, certificate validation and the separate
180-day inactivity cutoff still apply. The completion grace is configurable,
with an approved default of 24 hours from server preparation.

Grace expiry blocks ordinary operations with the old credential, not unattended
completion itself. If the client retains the pending replacement key, it can
confirm that replacement through the restricted completion path and resume
normal operations without new owner approval solely because grace expired.
Preserve the pending binding needed for this recovery while it remains
eligible under revocation and inactivity rules; optional short-lived response
receipts must not become an earlier forced-pairing deadline. Missing private
keys, owner revocation and the inactivity cutoff still require owner action.

Automation requires crash-safe credential replacement, bounded handling of
in-flight requests and old credentials, and recovery after interrupted issuance.
A stolen valid key could authorize routine rotation too; this is not compromise
recovery or a replacement for revocation. Existing owner-controlled lost-key
recovery remains separate. Certificate validity, overlap and rotation
of server/issuer keys remain open. No rotation mechanism is implemented.

### Technical proposal: interrupted routine rotation

This specifies proposed state handling within the approved rekey flow, not a
new cryptographic protocol or a completed implementation. Serialize rotation
for a server enrollment in the shared local credential store, so concurrent
CLI processes/helpers do not each generate a competing replacement. Persist
the pending private key before requesting issuance; keep the current key until
the replacement has been verified and activated. Neither key leaves the client.

Each rotation has a unique request identifier, the expected current credential
version and the proposed public key. Authenticate the request with the current
local credential and proof of the new key, bound to this server and enrollment.
Signing/issuance is preparatory. A server transaction records the pending
replacement, its recoverable issuance result and the fixed grace deadline;
the current credential remains active. Repeated requests return the same
pending result without extending that deadline. Routine rotation never
acquires owner-recovery authority.

The client verifies the returned credential/key/server/identity binding and
durably saves the replacement before confirming with proof of its new key.
A conditional server transaction activates it and records a recoverable result
only if the expected current state is still eligible and no owner recovery,
suspension or revocation has superseded it. Repeated confirmation returns the
same activation result; a conflicting proposal cannot overwrite it. If the
final response is lost, resolve that rotation using proof of the retained
old/pending key as permitted for that transaction. Do not mint another identity
or infer activation from a timeout. The restricted completion/retrieval path
cannot restore revoked access or permit ordinary operations past the grace
deadline using the old credential. Atomically promote the verified replacement
locally after resolving activation. Recovery receipts remain subject to bounded
retention.

Old-credential overlap must be explicitly bounded. Retired keys cannot keep
minting new rotations or undo an owner-approved replacement. Define admission
of already-started requests and test concurrent helpers, crash before/after
server commit, lost responses and revocation/recovery races. Do not automatically
replay a possibly executed upstream mutation to recover a credential exchange.

The former warn-versus-block question is superseded by the approved
confirmation-and-grace rule above. No immediate cutoff follows merely from
missing confirmation, and no indefinite use follows from withholding it.
Still specify handling of failures before the server can prepare a replacement,
bounded receipt retention and post-activation in-flight credential overlap;
these are not permission to bypass identity validation or extend the grace
deadline. The 30-day due threshold is not a certificate lifetime.

[EST](https://www.rfc-editor.org/rfc/rfc7030.html#section-4.2.3) is a precedent
for distinguishing credential issuance from immediate success and providing
retry information, not the selected Arbiter transport/authentication protocol.

### Technical proposal: durable rotation state and restart behavior

The server owns the clock and the rotation obligation. On the first
successfully authenticated connection at or after the 30-day key-age threshold,
it prepares one durable rotation record with a fixed 24-hour deadline. This
initiation must not depend on the client volunteering a new public key: a
client that withholds that key must not prevent the countdown from starting.
Here preparation means recording the rotation obligation; issuance of a
replacement certificate follows once the client supplies its new public key
and proves possession. Neither step activates that credential.

Persist at most one pending rotation per enrollment. Its record contains the
rotation identifier, server/enrollment references, expected current credential
version, preparation time, fixed grace deadline, phase, and any bound candidate
public key/issued certificate. The existing enrollment record retains current
key acceptance, account grants, access status and last authenticated use. A
replacement request cannot erase an existing obligation or give it a new start
time. These are internal state fields, not a selected wire encoding.

| Durable phase | Ordinary operations | Completion and recovery |
| --- | --- | --- |
| No pending rotation; not due | Current credential, subject to access checks | No replacement is required. |
| Prepared; no candidate bound | Current credential until the grace deadline | Enrolled client supplies a fresh key and proof within this same rotation. Withholding it does not postpone the deadline. |
| Candidate issued; unconfirmed | Current credential until the grace deadline | Client saves the candidate, then confirms with proof of its new private key. |
| Grace expired; unconfirmed | Reject the old credential for ordinary operations | Permit only authenticated steps that finish this same rotation; do not open a second grace period. |
| Activation committed | New credential for new ordinary requests | Repeat confirmation/status retrieval safely using the recorded binding; never repeat an upstream operation as part of this recovery. |
| Revoked, suspended or inactive | Deny service according to that access state | Completion cannot override the denial; owner intervention follows the existing recovery contract. |

Each state change rechecks the enrollment version and access state within a
short database transaction. Do network exchange, cryptographic work and file
I/O outside the transaction, then conditionally commit against the expected
version. If owner recovery or revocation wins the race, discard the stale
candidate/result; a later retry cannot reverse that change. Do not hold a
database transaction while waiting for client confirmation. SQLite's
[single-writer transaction model](https://www.sqlite.org/lang_transaction.html)
requires bounded lock waits and work outside the event loop.

On activation, stop accepting the old key for new ordinary requests. Already
admitted requests may finish under their existing budgets and revocation
checks; rotation alone is not an instruction to repeat or roll back their
upstream work. Shared-client processes reload the credential after resolving
the recorded activation instead of treating an old-key rejection as permission
to replay a possibly executed mutation. This bounds old-key use without
introducing parallel installation credentials or another overlap timer.

Keep the pending state until activation or an access-state transition makes it
ineligible. It is one record, not an unbounded retry journal. Keep the latest
activation binding with the accepted credential version so a lost final reply
can be resolved without an arbitrary short receipt timeout. A later rotation
or owner recovery supersedes that binding. Never use an old completion result
to roll back to an earlier version. Server restart retains preparation time and
deadline; client restart retains both the old and pending keys. Restore uses
the recovered snapshot's timestamps, subject to the already accepted stale-
snapshot warning, and does not silently restart the countdown.

Certificate validity and proof of possession are separate checks. Ordinary
operations still require a currently valid credential. The restricted
completion path must prove the keys bound to the remembered pending record;
it must not treat an expired certificate as valid ordinary authorization.
If a prepared certificate ages out before eligible late completion, fresh
issuance for the same bound candidate must preserve the original rotation
and deadline. The final issuer/validity profile must demonstrate this behavior
and compatibility with the 180-day inactivity rule; it is not yet selected.
See [RFC 5280 validation](https://www.rfc-editor.org/rfc/rfc5280.html#section-6.1.3).

Acceptance scenarios for implementation: refuse to supply a candidate; never
confirm; reconnect repeatedly across the deadline; lose either issuance or
activation reply; crash on either side of activation; run competing helpers;
race owner revocation/recovery; restart the server; return after grace but
before inactivity; and return after inactivity. Check exact deadline boundaries,
unchanged grants, no deadline extension, bounded pending state and no replayed
upstream mutation. These are required scenarios, not tests that have run.

### Agreed: inactivity cutoff and owner-approved pairing recovery

After 180 days without an authenticated client connection by default, disable
that client's credentials for service access and unattended rotation. The
client must pair again with owner approval. Measure activity from successfully
authenticated contact; arbitrary network traffic does not extend the period.
Rotation timing and inactivity are separate policies: rotation is due after
30 days of key age by default, while the inactivity cutoff is 180 days since
the last authenticated connection by default.

Recovery reuses the pairing experience for the existing identity. The owner
starts recovery on the client, which displays a one-time secret pairing code.
Through trusted server administration, initially local CLI or SSH, the owner
selects the existing client identity, supplies the code and approves replacement
of its credential. The client receives and stores the new credential directly.
Preserve identity, enrollment and account grants; existing suspensions and
revocations remain in effect. An expired credential may identify the record but
does not by itself authorize recovery. Exact commands and protocol remain open.

Certificate validity must be reconciled with the approved inactivity window.
Normal X.509 validation checks validity at the current time
([RFC 5280 section 6.1.3](https://www.rfc-editor.org/rfc/rfc5280.html#section-6.1.3)).
Do not introduce an earlier forced-pairing deadline through certificate expiry
or assume expired certificates are acceptable for normal operations. The
mechanism for maintaining certificate validity across permitted inactivity
remains to be designed.

Inactivity expiry disables abandoned credentials but does not detect a stolen
key whose holder continues to authenticate. Explicit revocation remains needed
for suspected compromise.

[EST re-enrollment](https://www.rfc-editor.org/rfc/rfc7030.html#section-4.2.2)
is a standards precedent distinguishing certificate renewal and rekeying, not a
selected protocol; its TLS-coupled authentication cannot simply be assumed to
satisfy Arbiter's transport-independent identity requirement.

This places identity-issuance authority in the trusted server. It simplifies
single-operator lightweight setup but does not provide an owner identity
independent of server control. Portability, issuer backup/migration and owner recovery still
need reconciliation with the agreed requirements. Owner approval must bind to
the intended client key; server-mediated provisioning does not itself solve
pairing or initial server verification. No implementation is authorized.

### Proposal: owner-signed agent identities

Historical exploration: AMI with X.509 is now selected for the first delivery.
External owner attestations and multi-owner delegation remain future work.
The earlier unsettled statements below do not reopen the selected AMI pairing
flow or its explicit approval requirement.

Owner registration precedes accepting an attestation as coming from a recognized
owner. For the initial trusted-operator deployment, a proposed flow is to
register an owner's public identity through trusted local/SSH server
administration and verify the owner's control of that identity. Its display
name is a label associated with the registered identity, not independent proof.
The owner's authority to enroll agents and grant accounts must be explicit;
recognizing an owner does not automatically grant all accounts or admit every
agent they sign for. This flow and its protocol have not been approved.

The owner proposes trusting an agent operator's cryptographic identity once and
accepting identities that operator signs for their agents. This preserves each
agent's separate key/identity while introducing an owner as a trusted issuer.
No certificate format or automatic-enrollment policy has been selected.

The design must use established identity and certification systems rather than
inventing an owner/agent identifier derivation or cryptographic binding scheme.
The owner requested research into systems supporting subordinate identities.

The design distinguishes certifying an agent's ownership from authorizing
its enrollment and service permissions. The agent owner may approve the agent
and grant specific accounts. Automatic enrollment based solely on a signature,
without individual approval, remains undecided, as do the owner's permitted
accounts and delegation limits. Owner signing credentials must remain separated
from the agents. Initial server verification remains open; trusting an agent's
issuer does not itself establish the server's identity.

### Known architectural risk and intended mitigation

In lightweight mode, the agent and code it runs can read its client private
key. Prompt injection or malicious code can cause disclosure, allowing an
attacker to impersonate that client independently of the original agent while
the credential remains accepted. The `NEVER SHARE THIS` warning is guidance;
it does not enforce key confidentiality. This is an accepted known risk of
lightweight mode, not a fixed vulnerability.

The intended mitigation places the agent runtime, shell and project code in
an isolated workload. A trusted broker outside that workload holds the private
Arbiter client key. The in-workload CLI requests Arbiter operations through a
narrow interface; the broker authenticates to the server and returns results
without exposing keys or portable authentication tokens. The interface must
restrict use to the authorized agent environment: an unrestricted host listener
would expose the client's authority to unrelated local actors even if the key
itself remained protected. The caller-verification mechanism remains open.

Arbiter and Reploy are complementary parts of this architecture. Arbiter owns
service credentials, enrolled-client account grants and operation policy. Reploy
owns the agent's network, filesystem and host isolation, which are needed
beyond protecting this client key. Reploy controlled sessions are the likely
integration mechanism; the exact integration remains to be designed. Isolation
assumes a trusted host and broker. It does not establish protection from a
malicious host administrator.

The broker exposes Arbiter operations rather than arbitrary signing or key
export. Server account grants and operation policies continue to apply. This
arrangement addresses key exposure under the isolation assumptions, but an
influenced agent can still request permitted operations or relay live access.
Neither sandboxing nor key custody establishes that an allowed operation
reflects the user's intent.

Implementation remains deferred until Reploy provides a sufficiently capable
sandbox. This architecture is not a prerequisite for initial authentication
or lightweight mode, and no integrated secure mode is implemented today.

Inspection of `../reploy` found controller/workload separation, but no Arbiter
broker integration. The current controlled-session runtime supports Linux
hosts running Docker, excludes Docker Desktop, rejects private-environment
injection, and has coarse bidirectional session networking. Revisit sandbox
capabilities, key provisioning/persistence, broker access and platform support
before claiming the mitigation is supported. No integration or isolation test
has run. Recording this architecture documents the risk and future mitigation;
it does not resolve the underlying exposure in lightweight mode.

### Proposal: device-bound client key custody

The user proposes storing the agent key encrypted and bound to its system,
while giving agent tools an unlock credential usable through that local Arbiter
client. This is an exploration, not selection of a key store or a guarantee.
The intended benefit is that copying the unlock credential and encrypted files
to another machine does not permit independent authentication there.

Distinguish encryption bound to an OS account/device from a non-exportable
signing key. If a client decrypts the private key into a process accessible to
agent-controlled code, local extraction remains possible. A protected signer
or hardware-backed non-exportable key can provide a stronger boundary, subject
to platform support, compatible algorithms and authenticated local access.
[Windows TPM documentation](https://learn.microsoft.com/en-us/windows/security/hardware-security/tpm/how-windows-uses-the-tpm)
describes signing without exposing key material to system memory, while
[DPAPI documentation](https://learn.microsoft.com/en-us/dotnet/standard/security/how-to-use-data-protection)
describes OS user/computer-scoped encryption rather than a unique client-binary
boundary. Machine identifiers or a copyable client executable are not secrets.

The unlock credential still authorizes use on the original system. Sharing it
can enable other local helpers or a live remote relay through that system;
neither a hardware key nor encrypted storage prevents permitted-operation
misuse through an accessible client. Keep identity/recovery authority separate
from runtime use, avoid returning portable bearer credentials to agent tools,
and assess revocation and freshness in the chosen protocol. Device replacement
would need the agreed owner-authorized credential replacement flow. No platform
prototype, isolation test or storage/authentication mechanism is approved.

Evaluate identity formats separately from the applications that use them.
The Buzz SDK's NIP-OA compute/verify operations use keys and signed data without
requiring a relay connection. A proposed lightweight route is built-in Arbiter
owner/agent setup using that existing format, with no Buzz workspace prerequisite.
This would require Arbiter-side tooling and lifecycle design; it is not an
already available owner wizard. X.509 with local certificate tooling is another
candidate: [Smallstep's certificate commands](https://smallstep.com/docs/step-cli/reference/certificate/create/)
can create and sign certificates locally without a separately running CA
service. Neither approach has been selected or tested as an Arbiter integration.

| [SPIFFE X509-SVID](https://spiffe.io/docs/latest/spiffe-specs/x509-svid/) and [SPIRE](https://spiffe.io/docs/latest/spire-about/spire-concepts/) | Standard workload identifiers in X.509 certificates, with trust domains and automated workload attestation/issuance. | Adds an established workload identity profile and lifecycle tooling. | [OpenSSH certificates](https://man.openbsd.org/ssh-keygen.1#CERTIFICATES) | A trusted CA signs independent client/host keys, with principals and validity restrictions. | Supports issuer-based trust, but its certificate format and authentication protocol are for SSH; using it for Arbiter's HTTPS API would require additional integration. |
| [Buzz NIP-OA Owner Attestation](https://github.com/block/buzz/blob/main/docs/nips/NIP-OA.md) | An owner signs an authorization for an independent agent public key; the agent retains its own authorship. | Direct fit for verifiable owner-to-agent provenance, with existing [verification code](https://github.com/block/buzz/blob/main/crates/buzz-sdk/src/nip_oa.rs). It is a Buzz draft extension, not a finalized general Nostr identity hierarchy or complete Arbiter authentication solution. |

### Agreed: mutable account grants

Keep the agent's cryptographic identity separate from its current account
grants, with server-controlled authorization state. Existing plugin policies
define the client's permitted use. Do not add a second policy or operation
allowlist on top merely because client identity is being introduced.

Preserve the existing operation flow. The client supplies a configured account
name; the plugin resolves that account, loads the policy named by its `policy`
field, and enforces that policy before performing the upstream operation.
The client does not independently select a policy. Authentication adds the
check that this client is allowed to use the requested account before this
existing path. Account-to-policy binding and plugin policy enforcement remain
unchanged. No client/account/policy reassignment, policy intersection or extra
operation allowlist is part of this work.

This is verified in SMTP's `_resolve_context`/`send_email` and IMAP's
`_resolve_account_config`/`_resolver`/`list_messages`, and matches the existing
plugin configuration guides. The earlier proposed policy remapping was an
assistant error, not an approved design change. Exact grant storage still needs
design. The current sole owner is also the operator and grants access to the
configured accounts; separate owner/operator authority is future hosting work.

Discovery and operation authorization would need to reflect allowed accounts;
hiding an account from discovery alone cannot prevent access by a caller who
knows its name. Owner-managed account grants are an agreed requirement, distinct
from signing identities or automatically approving enrollment. Future hosted
owners must have separate policies and account visibility; their agents must
not discover another owner's entries. This does not add multi-owner support
to the current delivery.

Approved grant continuity (D102, resolving U50): grants follow the configured
account name within its plugin. If the owner repoints `imap/personal` to a
different mailbox, existing grants for `imap/personal` cover the replacement.
Use a new configured account name and explicit grants when a separate access
boundary is intended. Password renewal does not require regranting. Preserve
the existing account-to-policy binding and enforcement; no upstream-account
fingerprint, account-generation approval or second policy layer is added.

### Exploration: protecting users from the operator

The owner has requested exploration of this possibility. No protection level or
architecture has been selected. This would change the present trusted-operator
assumption and requires distinguishing three goals: hiding reusable service
credentials, preventing unauthorized service operations, and hiding message
content from the operator.

Candidate approaches include provider-limited delegation, a user-controlled
connector that independently enforces authorization, and attested confidential
execution with independently controlled secret release. Encryption at rest alone
does not protect secrets once an ordinary operator-controlled runtime can decrypt
and use them. A connector must not blindly trust requests from hosted Arbiter;
confidential content also requires protected communication to a user-controlled
recipient. Confidential execution requires approved code/configuration and a
verification and key-release path the operator cannot override.

These are research options, not capabilities of the current implementation.

The owner has ruled out provider-specific delegation as the general solution
and emphasized keeping credentials away from the agent. The longer-term candidate
is a user-provided unlock key with confidential execution.
The platform, protection guarantees and release scope remain undecided pending
cost assessment. A connector would be a separate execution service, not the
existing Arbiter CLI; its deployment location would require its own trust model.

An enclave-based proposal must protect credential use and request authorization,
not just password decryption. It also needs an independently trusted attestation
and key-provisioning path, approved-code and policy update rules, encrypted
persistence, and recovery and availability behavior. No implementation estimate
or operating-cost estimate has yet been verified.
